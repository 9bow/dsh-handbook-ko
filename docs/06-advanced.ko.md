## TL;DR(본 장 핵심, 30초 버전)

1. **시간이 어디로 가는가**: 모델 사고가 ~90%, 도구 실행 <1%, 네트워크/렌더링 ~10% —— 사고 시간을 최적화하는 것이 가성비가 가장 높은 속도 개선책입니다
2. **3단계 전략**: `low`(단순/배치 라운드), `high`(일상 기본값), `max`(복잡한 추론/디버그) —— 수동으로 UI에서 선택하거나 플러그인이 자동으로 조절
3. **소요 시간 시각화**: Web UI 하단 통계 행(LLM Xs / 도구 호출 Ys)이 병목을 찾는 가장 빠른 방법입니다
4. **8개의 실제 트러블슈팅**: rc.1 의존성 단절, 플러그인 main 누락, next() await 누락, 이벤트 타입 인식 실패, client 테스트 실행 불가, 캐시 적중 오판, 포트 점유, 추론 직렬화 시 reasoning 유실(#739)

## 6.1 성능 모델: dsh의 시간은 어디로 가는가

"파일 생성" 작업 하나의 소요 시간 분포를 실측했습니다:

| 단계 | 비율 | 설명 |
|---|---|---|
| 모델 사고(Think) | ~90%(단일 저장소/명확한 위치 시나리오) | **매 도구 호출 전마다** 다시 사고하는 것이 절대적인 대부분을 차지 |
| 도구 호출/검색(Tool) | **다중 저장소 시나리오에서는 87%까지 역전 가능**([#2019](https://github.com/deepseek-ai/deepseek-harness/discussions/2019) 실측: LLM 4분 8초 / 도구 29분 17초) | workspace/에 여러 git 저장소가 있으면 harness가 저장소 사이를 헤매며 위치를 찾음 —— **검색/위치 확인 비용**이지 사고 비용이 아님; 범위를 명시하면 1분 만에 해결 |
| 도구 실행 | <1% | 파일 쓰기 등은 밀리초 단위 |
| 네트워크/렌더링 | ~10% | API 왕복 + UI 업데이트 |

**추론**:
- 단순 작업 → 사고 시간을 최적화(추론 강도 낮추기)
- 긴 도구 체인 작업 → 매 단계마다 사고 시간을 절약하면 누적 이득이 가장 큼
- 도구 자체가 느린 경우(검색/대용량 파일) → 강도 조절이 아니라 도구 구현을 최적화

## 6.2 reasoning_effort 전략(공식 3단계)

| 강도 | 시나리오 추천 |
|---|---|
| `low` | 단순/결정론적 라운드: 파일 조작, 배치, 도구 체인 중 저렴한 단계 |
| `high` | 일상적인 Agent 작업(기본값) |
| `max` | 복잡한 추론, 긴 체인 계획, 디버그 |

**수동**: UI의 "추론 등급" 선택기, 또는 `~/.dsh/settings.yaml`의 `reasoningEffort`.
**자동**: 플러그인이 도구 라운드에 따라 동적으로 강도를 낮춤(속도 개선 플러그인 예제, 제4장).

> "공식 3단계"는 기본 DeepSeek 어댑터(deepseek-official)에서는 off / high / max입니다; low는 pi-ai(opencode-go) 게이트웨이의 강도입니다(본 백서의 실측 환경, 즉 benchmark가 사용하는 게이트웨이). 도구 체인 강도 다운그레이드 서사는 게이트웨이 환경에서 성립하며, settings.yaml에서 기본 provider를 쓸 때는 off를 사용하세요.

## 6.3 도구 호출 소요 시간 시각화

dsh의 세션 통계 행(Web UI 하단)에는 다음이 표시됩니다: `N 라운드 · M 단계 | LLM Xs · 도구 호출 Ys | 첫 토큰 평균 ...` —— 이것이 병목을 찾는 가장 빠른 방법입니다.

심화: host 플러그인이 도구 이벤트를 감시해 도구별 시간을 측정합니다(속도 개선 플러그인 예제에 이미 host 로그 버전이 내장되어 있음), "어떤 도구가 가장 느린지"를 드러냅니다.

## 6.4 흔한 트러블슈팅 목록(실제 경험, 해법 포함)

| # | 트러블 | 증상 | 해법 |
|---|---|---|---|
| 1 | rc.1 의존성 단절 | `pnpm install` 404(`dsh-type-meta` 등이 게시된 적 없음) | 의존성은 `^0.1.0-rc.6` 라인 사용 |
| 2 | 플러그인에 main 없음 | `No "exports" main defined` | `.` 엔트리 노출; `"main": "src/index.ts"`는 tsx로 로드 가능 |
| 3 | `next()`에서 await 누락 | provider/model 유실로 오류 발생 | `agent/request`의 `next()`는 Promise를 반환하므로 반드시 await |
| 4 | 이벤트 타입 인식 실패 | `'agent/request' is not assignable to keyof Events` | npm이 타입 확장을 re-export하지 않아 경계에서 시그니처를 느슨하게 |
| 5 | client 테스트 실행 불가 | jsdom에서 `window.__ModuleLoader__` undefined 오류 | client 산출물이 dsh 부트스트랩 메커니즘에 의존, 컴포넌트 테스트는 공식 CI에서 실행 |
| 6 | 단순 작업이 "갑자기 빨라짐"에 대한 오판 | 1초 vs 110초 차이를 잘못 귀속 | DeepSeek context cache 적중도 속도를 높임 —— A/B 테스트는 완전히 새로운 prompt를 사용해야 함 |
| 7 | 포트 점유 | `dsh web`이 시작되지 않음 | `netstat -ano \| findstr 3080`으로 PID를 찾아 kill |
| 8 | 추론 직렬화 시 빈 reasoning 생략([#739](https://github.com/deepseek-ai/deepseek-harness/discussions/739)) | **검증 포인트**: `off`(thinking:disabled) 강도는 정상(`high`/`max`에서만 발생); `high`/`max`에서 도구 호출 라운드에 **사고 내용이 없을 때**, serializeAssistant의 `toolCalls.length > 0 && reasoning.length > 0` 조건이 빈 reasoning 필드를 생략함 → 다음 라운드 요청이 400 오류(invalid pi-ai replay state) | 버그로 판단(reasoning 자리 표시자를 유지해야 함): 수정 방향은 직렬화 시 해당 필드를 **항상 유지**하는 것 |

## 6.5 평가 관점: 공식 성적표 vs 독립 실측

(0813 정식 버전 출시와 결합하여) Agent 모델 성적표를 볼 때는 세 가지를 물어야 합니다:
1. **누가 측정했나**? 공식 자체 측정(자체 Harness) vs 독립 서드파티(AA 등)
2. **어떤 harness인가**? 프레임워크가 다르면 점수 차이가 큽니다(공식 Terminal-Bench 87.9 vs AA 독립 79)
3. **검증기는 얼마나 엄격한가**? 느슨한 검증기(SWE-bench Verified 8.5% 위양성) vs 엄격한 검증기(DeepSWE 0.3%)

dsh의 `agent/request` waterfall은 모델 성적을 재현 가능하게 만듭니다 —— 이것이 클로즈드소스 제품 대비 dsh의 엔지니어링 우위입니다.

## 6.6 캐시 전략: 매 호출을 더 저렴하게 만들기

제5장에서 고캐시 적중률의 가치를 다뤘습니다(실측 세션 캐시 적중률 97%; 캐시 할인 Flash 등급 98% / Pro 등급 99%+), 여기서는 **실행 가능한 전략**을 제시합니다:

| 목표 | 방법 |
|---|---|
| 적중률 높이기 | 긴 작업은 **세션 연속성 유지**(자주 새 세션을 만들지 않기) |
| 적중률 높이기 | 시스템 프롬프트/스킬 카탈로그 등 **접두사를 안정적으로 유지**(설정을 자주 바꾸지 않기) |
| 적중률 높이기 | 배치 작업은 같은 세션/같은 접두사에 두기(예: 같은 배치의 파일 분석) |
| 비용 낮추기 | 단순한 라운드는 `low` 등급 사용(사고 토큰 감소 → 총 토큰 하락) |
| 모니터링 | 세션 통계 행에서 "캐시 적중 %" 확인(Web UI 하단) —— 예상보다 낮으면 접두사 안정성을 점검 |

**비용 모델 요약**: `총 비용 ≈ 출력 토큰×출력 가격 + 입력 미적중×미적중 가격 + 입력 적중×적중 가격` —— Agent 워크로드는 입력 비중이 높아서, **캐시 적중률이 비용의 첫 번째 변수**입니다.

## 자주 묻는 질문 FAQ

**Q1: 왜 제 dsh가 "가끔은 유독 빠르고, 가끔은 유독 느린가요"?**
두 가지 주요 원인이 있습니다: ① DeepSeek context cache가 적중할 때는 첫 라운드 컨텍스트 주입이 훨씬 빨라집니다(1초 vs 110초 차이가 여기서 나올 수 있음); ② 추론 강도가 다르면 사고 시간이 몇 배 차이 납니다. A/B 비교 테스트를 할 때는 완전히 새로운 prompt를 사용하고(캐시 적중 방지) + 강도를 고정해야 합니다.

**Q2: 예제 속도 개선 플러그인이 실제로 얼마나 빨라지나요? 실측 데이터가 있나요?**
속도 개선 효과는 작업 유형에 따라 다릅니다. 단순 작업(1-3단계)은 dsh가 원래 빨라서 플러그인 효과가 뚜렷하지 않습니다. **긴 도구 체인 작업(20-50단계)에서 이득이 가장 큽니다**, 매 단계 사고 강도 다운그레이드의 누적 효과가 뚜렷하기 때문입니다. 구체적인 데이터는 제4장 예제 코드의 실측 로그를 참고하세요.

**Q3: 추론 강도를 `low`로 설정하면 모델 품질이 많이 떨어지나요?**
작업에 따라 다릅니다. 단순 파일 조작, 배치 처리, 결정론적 작업은 `low`를 써도 품질 차이가 거의 없습니다. 복잡한 추론, 긴 체인 계획, 디버그는 `low`를 쓰면 핵심 단계를 놓칠 수 있습니다. 권장: 일상에는 `high`를 쓰고, 배치/단순 작업은 수동으로 `low`로 전환하거나 속도 개선 플러그인으로 자동 다운그레이드하세요.

**Q4: 트러블 #6에서 말한 "context cache 적중"이 뭔가요? 적중 여부는 어떻게 판단하나요?**
DeepSeek API는 반복/유사한 컨텍스트를 캐시하며, 적중 시 첫 토큰 시간이 크게 단축됩니다. 판단 방법: dsh 세션 로그의 "첫 토큰 평균" 지표를 보고, 어느 순간 갑자기 10초+에서 1초 미만으로 떨어졌다면 캐시가 적중했을 가능성이 큽니다. 성능 비교 테스트를 할 때는 완전히 새로운 prompt를 사용해 캐시 간섭을 피하세요.

**Q5: rc 단계의 파괴적 변경이 성능에 영향을 미치나요? 업그레이드 후 무엇을 주의해야 하나요?**
영향을 줄 수 있습니다. rc 단계의 agent-loop, waterfall 시그니처, 플러그인 API는 모두 바뀔 수 있습니다. 업그레이드 후: ① `dsh --version`을 실행해 버전 확인; ② 공식 changelog에 breaking changes가 있는지 확인; ③ 익숙한 작업 하나를 실행해 소요 시간과 동작을 비교; ④ 커스텀 플러그인의 타입 호환성을 확인하세요.

**Q6: 성능 벤치마크 테스트를 하고 싶은데, 조언이 있나요?**
세 가지 원칙: ① 환경 고정(같은 모델, 같은 네트워크, 같은 강도); ② 캐시를 피하기 위해 완전히 새로운 prompt 사용; ③ 여러 번 실행해 중앙값을 취하기(단일 실행은 변동이 큼). 기록할 항목: 벽시계 시간, LLM 소요 시간, 도구 호출 소요 시간, 첫 토큰 시간. 본 장 6.1절의 소요 시간 분포 모델을 참고해 여러분의 benchmark를 설계하세요.
