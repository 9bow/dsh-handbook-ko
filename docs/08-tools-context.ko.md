# 제 8 장: 도구와 컨텍스트 시스템

> 본 장의 목표: dsh의 "능력 엔진"을 이해합니다 —— 모델이 어떤 도구를 호출할 수 있는지, 컨텍스트는 어떻게 모델에게 전달되는지, 그리고 긴 대화는 어떻게 처리되는지. **이것이 "돌아간다"에서 "왜 돌아가는지 안다"로 넘어가는 핵심 챕터입니다.**

## TL;DR(본 장 핵심, 30초 버전)

1. **60+개 공식 능력 패키지**: 도구(fs/shell/web/skill/todo), 컨텍스트(context/compaction), 세션, 서브에이전트, MCP, 워크플로우, 보안, 모델, 인터페이스 —— 모든 것이 플러그인입니다
2. **내장 도구 이름은 짧은 동사**: `read`/`write`/`grep`/`glob`/`edit`/`bash`/`todo`/`skill` —— 프롬프트를 쓸 때 "파일 읽어", "검색해"라고 하면 됩니다
3. **도구가 locations를 반환 → 산출물 추적**: 모델이 어떤 파일을 바꿨는지 UI가 바로 보여주고 열 수 있습니다(대화 끝의 산출물 칩)
4. **컨텍스트 = 시스템 프롬프트 + 스킬 카탈로그 + 대화 이력 + 도구 결과**: 계층별로 주입되며, 매 단계 요청마다 도구 스키마가 함께 전달됩니다
5. **긴 대화 자동 압축(compaction)**: 오버플로우 감지 → 이력 다듬기 → 선택적 요약 → 실패 시 오버플로우 에이전트로 라우팅. 중요한 정보는 프롬프트에 직접 적어두는 것을 권장합니다
6. **플러그인 동작을 무비용으로 검증 가능**: mock llm + headless + 감사 dump(#462) —— API key 없이도 waterfall 전달과 도구 주입을 검증할 수 있습니다
7. **도구 체인의 알려진 트러블슈팅 3가지**: code 모드 run_code/bash의 description required 무한 루프(#558/#581/#689); 스트리밍에서 도구 이름이 지워짐(#725 계열, FAQ 참고); run_code 내 상호작용 도구의 비동기 결과가 유실됨(#1476)

## 8.1 공식 능력 패키지 지도(60+개 개요)

dsh의 능력은 전부 패키지 형태로 제공됩니다(`packages/<group>/<name>`). 초보자가 가장 알아야 할 것들:

| 능력 영역 | 공식 패키지 | 역할 |
|---|---|---|
| **도구(tools)** | `fs/tool-fs`, `fs/tool-fs-search`, `fs/tool-str-replace-editor`, `shell/tool-bash`, `web`, `skill`, `todo` | 파일/터미널/웹페이지/스킬/할일 등 호출 가능한 도구 |
| **컨텍스트(context)** | `context/*`, `compaction/*` | 요청 컨텍스트 조립, 긴 대화 압축 |
| **세션(session)** | `session/*` | 영속화, 제목, 텔레메트리 |
| **서브에이전트(subagent)** | `subagent/*` | 하위 작업 위임 |
| **MCP** | `mcp/*` | MCP 클라이언트(외부 도구 서버) |
| **워크플로우(workflow)** | `workflow/*` | 다단계 워크플로우 오케스트레이션 |
| **보안(safety)** | `sandbox/*`, `guard/*`, `interaction/*`, `credentials/*` | 샌드박스, 루프 위생, 권한/승인, 자격 증명 격리(참고: 공식에는 독립된 `safety/` 그룹이 없으며, 보안 정책은 여러 패키지 그룹에 분산되어 있음) |
| **모델(llm)** | `llm/*`, `llm-deepseek`, `llm-retry` | 모델 연동, 재시도 |
| **스킬(skill)** | `skill/*` | 스킬 프로바이더 레지스트리 |
| **인터페이스(client)** | `client/*`(ui-conversation, ui-tool…) | Web UI 각 구성요소 |

> **전체 목록과 패키지 수 기준**: 공식 저장소 `packages/README.md`가 패키지 목록의 권위 있는 표입니다(47개 그룹); `@deepseek-ai/dsh` CLI의 0.1.0-rc.6은 **53개의 `@deepseek-ai/dsh-*` 직접 의존성**을 선언하며(+CLI 자체 = 54), 계열 전체 게시 수는 약 **221개**입니다(devDeps와 과거 0.0.1-rc.1 라인 포함, 공식 빌드 커밋에서 언급). 백서/공식이 말하는 "60+"는 `packages/` 아래의 모든 하위 디렉터리를 가리킵니다. **npm 패키지 이름 표기법**(`@deepseek-ai/dsh-*`)과 **저장소 경로 표기법**(`fs/tool-fs`)의 대응 관계, 그리고 각 패키지의 실측 설명은 [부록 B: 공식 패키지 빠른 참조](./appendix-packages.md) 참고.
>
> 📚 **아키텍처를 더 깊이 알고 싶다면**: 공식 `docs/subsystems/`(session / system-prompt / tools / agent / agent-loop / scope / llm-streaming / subagent)는 각 서브시스템의 설계 문서로, 이 절의 "능력 영역 그룹화"보다 훨씬 체계적입니다; 자동 생성된 공식 목록은 공식 `docs/tool-catalog.md`, `docs/config-catalog.md`, `docs/module-graph.md` 참고.

## 8.2 내장 도구(실측 관찰)

모델이 실제로 호출할 수 있는 도구 이름은 **짧은 동사**입니다(실측 기록, dsh web 세션과 agent/request 로그 기반):

| 도구 이름 | 역할 | 비고 |
|---|---|---|
| `read` | 파일 읽기 | fs 능력 |
| `write` | 파일 쓰기 | fs 능력 |
| `grep` | 내용 검색 | fs-search |
| `glob` | 파일 패턴 매칭 | fs-search |
| `edit` / `str_replace_editor` | 정밀 편집 | 도구 결과에 locations 포함(산출물 추적용) |
| `bash` / `pwsh` | 명령 실행 | 샌드박스 격리 |
| `todo` | 할 일 관리 | 긴 작업 계획 |
| `skill` | 스킬 호출 | skill-catalog 주입 |

**도구 결과와 산출물 추적**(중요한 개념): 도구의 반환값에는 `locations`(파일 경로)가 포함되어 있으며, dsh는 이를 이용해 "산출물 파일 행"을 만듭니다(대화 끝의 산출물 칩이 여기서 나옵니다) —— **모델이 어떤 파일을 바꿨는지 UI가 바로 보여주고 열 수 있습니다**.

## 8.3 컨텍스트는 어떻게 모델에게 전달되는가

모델 요청 한 번의 컨텍스트 = 시스템 프롬프트 + 스킬 카탈로그 + 대화 이력 + 도구 결과. 세션 로그에서 실측으로 확인할 수 있습니다:

```text
컨텍스트 주입 @deepseek-ai/dsh-system-prompt   ← 공식 시스템 프롬프트
컨텍스트 주입 skill-catalog                    ← 스킬 카탈로그
```

dsh의 컨텍스트 메커니즘:
- **시스템 프롬프트 계층화**: 공식 플러그인이 `systemPrompt.section()`으로 프롬프트 조각을 등록(예: ui-deliverables가 "산출물 파일 참조" 안내를 등록)
- **스킬 카탈로그 주입**: 사용 가능한 스킬 목록이 컨텍스트에 들어가, 모델이 필요에 따라 호출
- **도구 스키마**: 매 단계 요청마다 도구 정의가 함께 전달됨

### 8.3.1 PTC 모드(Code mode): 코드 한 조각으로 여러 라운드의 도구 호출을 오케스트레이션

**PTC = Programmatic Tool Calling(프로그래매틱 도구 호출)** —— 공식 중국어 사이트는 "PTC 모드"라고 부르고, 공식 영문 페이지는 이에 대응해 **Code mode**라고 합니다([#1052](https://github.com/deepseek-ai/deepseek-harness/discussions/1052) 댓글의 커뮤니티 상세 설명; 공식 사이트 원문: "PTC 모드는 모델이 생성한 코드 조각을 통해 여러 라운드의 도구 호출을 조합합니다").

**전통적인 방식과의 차이**: 표준 모드에서는 모델이 **매 단계마다 도구 호출을 한 번씩 발행**합니다(한 단계마다 한 번의 왕복); PTC 모드에서는 모델이 **TypeScript 프로그램 한 조각을 생성**해, 단일 프로그램 안에서 여러 라운드의 도구 호출을 오케스트레이션합니다(루프, 분기, `Promise.all` 병렬), 전체 프로그램이 한 번의 왕복으로 실행 완료됩니다:

| 항목 | 표준 모드 | PTC 모드(Code mode) |
|---|---|---|
| 호출 형태 | 단계마다 도구 호출 한 번 | 프로그램 하나로 여러 라운드 호출 오케스트레이션 |
| 모델 왕복 | 5회 호출 ≈ 5회 왕복 | 1회 왕복으로 통합 |
| 중간 결과 | 단계별로 컨텍스트에 다시 채워짐 | `return`/`console.log`만 다시 채워짐 |
| 전형적인 시나리오 | 일상 대화, 단일 단계 작업 | 긴 체인 자동화, 결정론적 실행 |

**실행 메커니즘**: 프로그램은 `@deepseek-ai/dsh-code-runtime-worker-thread`로 전달되어 **완전히 새로운 Node worker 스레드**에서 실행됩니다(타입 스트리핑 후 TS를 지울 수 있음; 빈 환경 + 힙/소요시간/출력 예산 + 강제 종료); 프로그램 내의 각 하위 도구 호출은 여전히 완전한 도구 파이프라인을 거칩니다(권한, 샌드박스, 감사가 그대로 적용됨).

**이점**: 여러 단계 호출이 한 번의 왕복으로 통합되고 + 중간 결과가 더 이상 전부 컨텍스트에 다시 채워지지 않음 → **token 비용이 크게 감소**합니다(#1052 댓글의 실측 경험: PTC 모드는 긴 작업의 비용 절감 수단 중 하나).

> 참고: PTC 모드에도 커뮤니티가 보고한 알려진 트러블슈팅이 있습니다 —— `run_code`/`bash`의 description required 무한 루프(8.8절 트러블 1 참고); 그리고 긴 세션에서 여러 라운드의 도구 호출 중간 산출물이 여전히 컨텍스트에 남습니다(#1052 원문 실측: 7천만→1억 토큰 폭증이 바로 PTC 모드에서 발생, 8.4절 자동 압축 필요성 참고).

## 8.4 긴 대화: compaction(압축)

긴 대화는 컨텍스트를 터뜨릴 수 있습니다. dsh의 `compaction` 플러그인(예: `compaction-basic`)이 담당하는 것:
- 컨텍스트 오버플로우 감지(`agent/request-error`의 `CONTEXT_WINDOW_EXCEEDED`)
- 이력 압축(모델과 무관한 다듬기 + 선택적 요약)
- 실패 시 "오버플로우 에이전트"(overflow agent)로 라우팅

> **자동 압축은 커뮤니티에서 자주 요청되는 기능입니다**([#1052](https://github.com/deepseek-ai/deepseek-harness/discussions/1052)): 사용자들은 긴 세션에서 토큰이 폭증한 후 "새 세션을 열어야 하는" 것이 고통스럽다고 피드백하며, **수동으로 새 세션을 여는 대신 자동 압축**을 원합니다 —— 커뮤니티 답변에서 "현재 내장된 자동 압축은 없는 것 같다"고 확인했습니다(compaction 플러그인 설치/수동 compact 필요). 저비용으로 긴 세션을 이어가는 임시 방법: 새 세션으로 바꾸기 + 필요에 따라 기억 주입(기억 계층화 방안은 제7장 7.3절과 제14장 14.7절 생태계 도구 참고).

> 초보자에게: **"긴 대화는 자동으로 압축된다"는 것만 알면 됩니다**, 세부사항은 심화 주제입니다. 프로덕션 환경 주의사항: 압축은 세부 정보를 잃어버리므로, 중요한 컨텍스트는 프롬프트에 수동으로 적어두는 것을 권장합니다.

## 8.5 권한과 보안 모델(알아만 두면 됨)

- **접근 모드**: UI에서 "Workspace Write" 등의 모드(권한 프리셋)를 볼 수 있음
- **상호작용 승인**: `interaction/*`이 권한/승인 능력을 제공(위험한 작업은 확인을 요구할 수 있음)
- **샌드박스**: `sandbox/*`가 명령 실행을 격리(예: pwsh 샌드박스는 ACL 제약이 있음 —— 실측 중 temp 디렉터리 권한 문제를 겪은 적 있음)
- **도구 타임아웃**: `guard/*`가 loop 위생과 도구 타임아웃을 제공

> 보안 설정의 심화 주제는 본 백서의 범위를 벗어납니다; 핵심 인지: **dsh의 도구 실행에는 기본적으로 격리와 승인 레이어가 있으며**, 맨몸으로 실행되지 않습니다.

## 8.6 초보자가 가장 기억해야 할 세 가지

1. **도구 이름은 짧은 동사입니다**(read/write/grep/glob/edit/bash) —— 프롬프트/플러그인을 작성할 때 "파일 읽어", "검색해"라고 직접 말하면 됩니다
2. **도구가 locations를 반환 → 산출물 추적** —— 모델이 수정한 파일이 대화 산출물 영역에 나타납니다
3. **긴 대화는 자동 압축됩니다** —— 이력을 수동으로 정리할 필요는 없습니다(단, 중요한 정보는 프롬프트에 적어두세요)

## 8.7 플러그인 런타임 검증 방법론(무비용)

> 출처: 공식 디스커션 [#462](https://github.com/deepseek-ai/deepseek-harness/discussions/462) 「DSH 플러그인 런타임 검증 방법론: API Key 없이 waterfall 동작 검증하기」(실측 74개 이벤트 / 12개 waterfall). FAQ에 이미 한 줄 요약이 있으며, 본 절에서는 자세히 다룹니다.

**페인 포인트**: 정적 점검은 "플러그인이 로드될 수 있는지"만 증명할 뿐, "플러그인이 실제 agent 루프에서 동작을 망가뜨리지 않는지"는 증명하지 못합니다. 특히 waterfall 이벤트 리스너(`tools/execute`, `approval/request`, `fs/write-intent` 등)는 반드시 `next()`를 올바르게 전달해야 하며, 그렇지 않으면 **다운스트림의 기본 동작을 조용히 삼켜버립니다** —— 이런 종류의 오류는 런타임에서만 드러납니다; 그런데 전통적인 검증은 실제 LLM API key와 토큰 비용을 필요로 합니다.

**무비용 방안**(dsh 저장소에 내장되어 있어 API key 불필요):
1. **mock llm**: 스크립트화된 반환값 —— 첫 요청이 "bash 도구 호출"을 반환하고, 두 번째는 정상 응답하도록(`--sequence tool_call_success,success`), 이렇게 도구 호출을 주입
2. **headless profile**: 실제 agent 루프를 거치며, 여러분의 플러그인이 리스너를 걸어둠
3. **감사 dump**: `DSH_EVENT_AUDIT_DUMP`가 이벤트 감사 스냅샷을 내보냄

```sh
# 1. mock-llm 시작(스크립트로 "bash 도구 호출" 주입)
pnpm run mock:llm --port 8000 --api-key mock-key \
  --sequence tool_call_success,success --repeat-last \
  --tool-name bash --tool-arguments '{"command":"ls"}'

# 2. headless agent 실행(mock-llm을 가리키며, 감사 내보내기)
DEEPSEEK_BASE_URL=http://127.0.0.1:8000/v1 \
DEEPSEEK_API_KEY=mock-key \
DSH_EVENT_AUDIT_DUMP=/tmp/audit.json \
pnpm dsh --profile headless "run the bash tool once and report"
```

**통과 판정**: 감사 스냅샷의 `byMode`에 emit과 waterfall이 모두 포함되고, waterfall 체인이 완전하게 나타나며, agent가 정상적으로 완료됨(`mock response recovered`). 실측: 74개 이벤트 / 12개 waterfall이 전부 캡처되며, 완전한 생명주기 `session/created → … → tools/pre-execute(wf) → tools/execute(wf) → tools/post-execute(wf) → tools/result`; 핵심 보안 증명은 **모든 waterfall 리스너가 `next()`를 올바르게 전달하고, 부작용이 전혀 없다는 것**입니다 —— 플러그인이 기본 동작을 삼키지 않고, mock으로 주입한 도구 호출도 체인을 완전히 거칩니다.

**소스 코드로 실행할 때의 세 가지 유의점**(#462 작성자의 실측 경험): sparse clone은 한 번에 전부 가져와야 함(`vendor/`가 빠지면 `Cannot find package '@deepseek-ai/cordis'` 오류); `build:lib:host` + `build:lib:client` + web-frontend dist 3층 빌드 중 하나라도 빠지면 안 됨; `mock:llm` 파라미터 앞에 `--`를 추가로 넣지 말 것(위치 인자로 처리됨).

## 8.8 도구 체인 트러블슈팅

rc.6 시대 도구 체인의 알려진 트러블슈팅(트러블 1/2는 이미 [FAQ](./faq.md)에 반영됨):

**트러블 1: code 모드 `run_code`/`bash`의 description required 무한 루프**([#558](https://github.com/deepseek-ai/deepseek-harness/discussions/558) [#581](https://github.com/deepseek-ai/deepseek-harness/discussions/581) [#689](https://github.com/deepseek-ai/deepseek-harness/discussions/689))
`code` 모드에서 `run_code`와 `bash` 둘 다 UI 요약 필드를 `description`이라고 부르고 required로 표시합니다: 모델이 종종 내부의 `bash.description`을 이미 전달한 것으로 착각해, 외부 JSON에는 `{"code":"..."}`만 남게 되어 → 반복적으로 `missing required property "description"` 오류가 발생하며, 마치 "무작위로 파라미터가 빠지는" 것처럼 보입니다. `#581`이 근본 원인을 보충합니다: `ToolArgsError`가 도구 이름을 포함하지 않아서, 모델이 어느 도구에서 오류가 났는지 파악할 수 없음 → 무한 재시도 루프(cherry-pick 가능한 수정 첨부); `#689`는 같은 계열의 문제로 인해 run_code 내의 모든 `tools.*` 호출이 거부되는 것을 보여줍니다. 회피법: 외부 description을 수동으로 보충하거나 표준 모드로 전환.

**트러블 2: 스트리밍에서 도구 호출 이름이 지워짐**([#725](https://github.com/deepseek-ai/deepseek-harness/discussions/725) 계열, 이미 [FAQ](./faq.md)에 반영됨)
증상: 모든 도구 호출에서 `Error: unknown tool ""` 오류가 발생. 근본 원인: SSE 스트리밍 파싱이 누적이 아닌 덮어쓰기 할당을 사용해, 도구 이름/ID를 빈 문자열로 지워버림([#725](https://github.com/deepseek-ai/deepseek-harness/discussions/725) 근본 원인 + 수정; [#161](https://github.com/deepseek-ai/deepseek-harness/discussions/161) [#615](https://github.com/deepseek-ai/deepseek-harness/discussions/615) [#694](https://github.com/deepseek-ai/deepseek-harness/discussions/694) [#741](https://github.com/deepseek-ai/deepseek-harness/discussions/741) 같은 계열). 공식 수정 전에는 다운그레이드하거나 버전을 기다릴 수밖에 없습니다; 모델이 반복적으로 재시도할 수 있으니 제때 중단하는 데 유의하세요.

**트러블 3: `run_code` 내에서 상호작용 도구 호출이 "삼켜짐"**([#1476](https://github.com/deepseek-ai/deepseek-harness/discussions/1476))
`run_code` 프로그램 안에서 상호작용 도구(예: `ask_user_question`)를 호출할 때: 동기 실행이 비동기를 기다리지 않음 —— 4ms 만에 빈 값을 반환; 비동기 결과가 약 12초 후에 돌아왔을 때는 세션 프레임이 이미 종료되어, 그대로 유실됩니다. `run_code` 실행 모델의 문제로 판단됩니다(비동기 도구 콜백을 지원하거나 pending 상태를 반환해야 함), AGENTS.md의 "코드 안에서 상호작용 도구를 호출하지 말라"는 규약은 근본적인 해결책이 아닙니다.

---

> **기억 방향 제안(#1822 커뮤니티 설계)**: 커뮤니티가 "기억체"(Memory Body)를 제안했습니다 —— 세션 간, 격리된, 사용자가 명시적으로 장착하는 기억 단위로, "기억이 뒤죽박죽 섞이는" 문제(세션이 끝나면 로그가 즉시 무효화됨 / session-reference는 @멘션 3개 소스만 다루고 본문은 검색하지 않음)를 해결합니다. 기억 계열(시나리오별로 주입하는 dsh-sgme / dsh-memory / AgentSoul)과 같은 방향으로 상호 보완합니다: 기억체는 하부 장착 단위를 담당하고, 상위 플러그인이 이를 재사용할 수 있습니다.

## 자주 묻는 질문 FAQ

> 본 장은 도구/컨텍스트에 관한 고빈도 문답을 아래에 다룹니다; 더 많은 일반적인 질문은 [FAQ 빠른 참조](./faq.md) 참고.

**Q1: 도구 이름이 `read`/`write` 같은 짧은 동사인데, 프롬프트를 쓸 때도 이 이름을 써야 하나요?**
아닙니다. "이 파일을 읽어줘", "foo가 포함된 줄을 검색해줘"라고 쓰면, 모델이 자동으로 해당 도구에 매핑합니다. 짧은 동사 이름은 플러그인 내부 구현 세부사항이며, 프롬프트는 자연어를 쓰면 됩니다.

**Q2: `edit`과 `str_replace_editor`는 같은 도구인가요?**
맞습니다. `str_replace_editor`는 내부 패키지 이름이며, 모델이 호출할 때는 `edit`으로 표시될 수 있습니다. 기능은 동일합니다: 파일의 특정 텍스트를 정밀하게 교체. 도구 결과의 `locations`는 산출물 추적에 사용됩니다.

**Q3: compaction 압축 후에도 모델이 이전 대화 내용을 기억하나요?**
"요약"은 기억하지만 세부사항은 잃어버립니다. compaction은 이력을 다듬고 + 선택적으로 요약을 생성하며, 핵심 정보는 남지만 세부사항은 유실됩니다. 그래서 중요한 컨텍스트(프로젝트 제약사항, 특수 요구사항 등)는 시스템 프롬프트나 프롬프트에 적어두고, 대화 이력에만 의존하지 않는 것을 권장합니다.

**Q4: `context/*`와 `compaction/*`는 무엇이 다른가요?**
`context/*`는 "매 요청의 컨텍스트를 조립하는" 역할입니다(시스템 프롬프트 + 스킬 카탈로그 + 대화 이력 + 도구 스키마). `compaction/*`는 "긴 대화를 압축하는" 역할입니다(오버플로우 감지 → 다듬기 → 요약). 하나는 "무엇을 담을지"이고, 다른 하나는 "담을 수 없을 때 어떻게 압축할지"입니다.

**Q5: 보안 모델에서 "샌드박스"와 "상호작용 승인"은 무엇이 다른가요?**
샌드박스(`sandbox/*`)는 명령 실행 환경을 격리합니다(예: pwsh 샌드박스는 ACL 제약이 있어 파일 접근을 제한). 상호작용 승인(`interaction/*`)은 "위험한 작업 전에 사용자 확인을 요구하는" 것입니다(파일 삭제, 알 수 없는 명령 실행 등). 하나는 "어디서 실행하는지"를 관리하고, 다른 하나는 "실행할 수 있는지 없는지"를 관리합니다.

**Q6: dsh에 새 도구(예: "데이터베이스 조회")를 추가하고 싶은데, 어떻게 해야 하나요?**
두 가지 방법이 있습니다: ① host 플러그인을 작성해 `ctx.provide`로 도구 서비스를 등록(제3장 3.4절 확장 포인트 참고); ② MCP로 외부 도구 서버를 연동(제9장 9.1절). 전자는 깊은 통합에 적합하고, 후자는 기존 시스템을 빠르게 연결하는 데 적합합니다.
