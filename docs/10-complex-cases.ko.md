# 제 10 장: 복잡한 실전 사례(dsh가 실제로 해낸 것)

> 본 장의 목표: **dsh에서 실제로 완료된 복잡한 작업 두 가지**를 통해, 다단계 도구 체인에서 dsh의 실제 능력, 산출물 품질, 소요 시간을 보여드립니다.
> **개인정보 안내**: 두 사례 모두 **합성 데이터/가상 코드**를 사용하며, 실제 비즈니스 데이터나 민감한 정보는 전혀 포함하지 않습니다.

## TL;DR(본 장 핵심, 30초 버전)

1. **사례 A(데이터 품질 분석, 186초)**: 52줄의 지저분한 데이터 → 분석 → 정제 스크립트 → 시각화 → 실행 검증, 52→35줄로 정리, 모든 문제 해결
2. **사례 B(5개 버그 수정 + 49개 테스트, 94초)**: 의도적으로 버그 5개를 심은 계산기 모듈 → 전부 수정 → 49개 테스트 전부 통과, 경계/정밀도/예외 커버
3. **dsh의 특징**: 다단계 도구 체인 자동 오케스트레이션, 판단력 있음(데이터 트레이드오프를 능동적으로 설명), 산출물 추적 가능, 소요 시간 제어 가능(94-186초)
4. **핵심 시사점**: 프롬프트에 검수 기준을 명확히 쓰면(예: "실행 검증"), dsh가 그대로 폐루프를 완성합니다 —— 복잡한 작업에는 "무엇을 할지 + 어떻게 검수할지"를 명확히 할 것을 권장합니다
5. **실패 복구**: 본 사례에서는 트리거되지 않았습니다; 프로덕션 환경에서는 guard 타임아웃 + 사람의 승인을 설정할 것을 권장합니다

## 사례 A: 데이터 품질 분석 + 정제 + 시각화(186초)

### 작업

지저분한 데이터가 포함된 합성 JSON을 dsh에 제공합니다(52줄: 결측값, 타입 오류, 중복 행, 이상치 99999), 요구사항:
1. 데이터 품질 문제 분석
2. 정제 스크립트 `clean.py` 작성
3. 시각화 스크립트 `visualize.py` 작성(`chart.png` 생성)
4. 두 스크립트를 실행해 검증

### dsh가 한 방법(도구 체인)

```text
read(sales_data.json) → write(clean.py) → bash(python clean.py)
→ write(visualize.py) → bash(python visualize.py) → read(출력) → 요약
```

### 산출물과 검증

| 산출물 | 결과 |
|---|---|
| `clean.py` | ✅ 실행 성공, 52 → **35줄**, 모든 문제 해결 |
| `visualize.py` + `chart.png` | ✅ 유효한 PNG 생성(1950×825) |
| 정제 전략 | 결측 금액은 중위수로 채움, 이상치 삭제, 중복 제거, 타입 통일 |

![dsh가 생성한 매출 시각화(사례 A 산출물)](./assets/case-chart.png)

### 출력의 핵심 포인트(판단력을 보여줌, 기계적 실행이 아님)

> - 중위수로 채우면 히스토그램에 510 스파이크가 생김 —— 대체값 처리의 고유한 부작용이니 설명이 필요함
> - 99999가 실제 대규모 주문이라면, 일괄 삭제 대신 IQR/분위수 방법을 쓰는 것이 좋음
> - 정제 후 통계: N=35, 평균 489.43, 중위수 510, 표준편차 181.73

**dsh는 작업을 실행했을 뿐 아니라, 데이터 처리의 트레이드오프와 가정을 능동적으로 설명했습니다** —— 이것이 agent 엔지니어링 레이어가 "생각한다"는 증거입니다.

## 사례 B: 5개 버그 코드 수정 + 49개 테스트(94초)

### 작업

**의도적으로 버그 5개를 심은** Python 계산기 모듈을 dsh에 제공합니다, 요구사항: 모든 버그를 찾음 → 수정 → 완전한 단위 테스트 작성 → 실행 검증.

### 심어놓은 버그

1. `add`가 `a - b`로 잘못 작성됨
2. `divide`가 0으로 나눌 때 조용히 0을 반환함(예외를 던져야 함)
3. `factorial`이 음수일 때 조용히 -1을 반환함(예외를 던져야 함)
4. `factorial`의 `range(1, n)`이 n을 곱하는 것을 빠뜨림
5. `format_money`가 소수점 둘째 자리로 포맷되지 않음

### dsh의 수정 + 테스트(검증: 49 passed)

전체 테스트는 [case-test-calculator.py](./assets/case-test-calculator.py) 참고 —— 49개 케이스가 커버하는 것:

| 함수 | 커버리지 |
|---|---|
| `add` | 양수/음수/0/부동소수점/정밀도/교환법칙 |
| `subtract` | 음수 결과/0 경계/부동소수점 |
| `multiply` | 부호 조합/0 곱셈/부동소수점 |
| `divide` | 정수 나눗셈/부호/부동소수점/**0으로 나누면 반드시 ZeroDivisionError를 던져야 함** |
| `factorial` | 0!/1! 경계/알려진 값/**음수는 반드시 ValueError를 던져야 함** |
| `format_money` | 0 채우기/반올림/**0.1+0.2 반올림**/음수 |

```bash
python -m pytest test_calculator.py -v   # 49 passed in 0.37s
```

### 관찰: dsh의 성과

- **완전한 폐루프**: 읽기 → 수정 → 테스트 작성 → 테스트 실행 → 요약, 사람의 개입 없음
- **수정 품질**: 5개 버그 전부 수정하고 docstring 설명도 보충
- **테스트 설계**: 경계(0으로 나누기/음수/정밀도)를 커버, "돌아가기만 하면 된다"는 수준이 아님

## 사례 요약: 복잡한 작업에서 dsh의 특징

| 항목 | 성과 |
|---|---|
| 다단계 도구 체인 | ✅ 자동 오케스트레이션(읽기→쓰기→실행→검증→요약) |
| 복잡한 작업 소요 시간 | 94초-186초(같은 모델, 같은 게이트웨이, benchmark의 단순 작업보다 느리지만 제어 가능) |
| 산출물 품질 | ✅ 판단력 있음(데이터 트레이드오프 설명, 테스트 경계 설계) |
| 산출물 추적 | ✅ 생성된 파일을 대화 끝에서 바로 열 수 있음 |
| 실패 복구 | 본 사례에서는 트리거되지 않음; 프로덕션에서는 guard 타임아웃 + 사람의 승인을 권장 |

**초보자에게 주는 시사점**: dsh는 "여러 파일, 여러 단계, 검증이 필요한" 작업을 능숙하게 처리합니다 —— 이것이 Agent 런타임으로서 dsh의 주요 가치 시나리오이기도 합니다. 복잡한 작업에는: 프롬프트에 **검수 기준을 명확히 쓸 것**을 권장합니다(예: "실행 검증"), 그러면 dsh가 그대로 폐루프를 완성합니다.

## 자주 묻는 질문 FAQ

**Q1: 사례 A는 186초, 사례 B는 94초 걸렸는데, 이 속도는 빠른 편인가요 느린 편인가요?**
작업 복잡도와 모델 강도에 따라 다릅니다. 같은 모델, 같은 게이트웨이 기준으로, benchmark의 단순 작업보다는 느리지만 제어 가능한 수준입니다. 핵심은 절대적인 속도가 아니라 "다단계 도구 체인 자동 오케스트레이션 + 산출물 품질 + 사람의 개입 없음"이라는 종합적인 가치입니다. 속도를 높이고 싶다면 제6장의 추론 강도 전략 + 속도 개선 플러그인 예제를 참고하세요.

**Q2: 사례에서 "합성 데이터"란 무엇인가요? 왜 실제 데이터를 쓰지 않나요?**
개인정보 보호 때문입니다. 본 백서는 실제 비즈니스 데이터나 민감한 정보를 다루지 않습니다. 합성 데이터는 "의도적으로 구성한, 실제 정보를 포함하지 않는 데이터"로, dsh의 능력을 시연하는 데 사용됩니다. 여러분 자신의 환경에서는 실제 데이터를 쓸 수 있지만, 데이터 보안에 유의해야 합니다.

**Q3: dsh가 복잡한 작업에서 "막혔다면"(예: 특정 단계의 도구 호출이 실패) 어떻게 해야 하나요?**
몇 가지 대처법: ① dsh 프로세스 로그를 보고 어느 단계에서 실패했는지 위치 확인; ② 도구 호출의 입력이 올바른지 확인(파일 경로, 명령 문법 등); ③ guard 타임아웃을 설정해(`guard/*` 패키지) 무한 대기를 방지; ④ 프로덕션 환경에서는 사람의 승인을 설정해(`interaction/*`) 위험한 작업 전에 확인하는 것을 권장합니다.

**Q4: 사례 B의 49개 테스트는 dsh가 자동 생성한 것인데, 품질은 어떤가요?**
품질이 괜찮습니다. 경계(0으로 나누기/음수/정밀도), 예외(특정 예외를 반드시 던져야 함), 일반(양수/음수/0/부동소수점)을 커버했습니다. 하지만 자동 생성된 테스트는 "비즈니스 로직 고유의 경계"를 놓칠 수 있으니 —— 테스트 설계를 사람이 리뷰하고, 도메인 특화 케이스를 보충하는 것을 권장합니다.

**Q5: dsh에게 "여러 파일, 여러 단계"의 작업을 시키고 싶은데, 프롬프트를 어떻게 써야 효과가 가장 좋을까요?**
세 가지 원칙: ① 목표를 명확히("무엇을 할지"); ② 검수 기준을 명확히("어떻게 완료로 판단할지", 예: "실행 검증", "49개 테스트 전부 통과"); ③ 제약을 명확히("무엇을 하면 안 되는지", 예: "원본 데이터를 삭제하면 안 됨"). 본 장 두 사례의 프롬프트 구조를 참고하세요.

**Q6: 사례 요약에서 "실패 복구는 본 사례에서 트리거되지 않았다"고 했는데, dsh의 실패 복구 능력은 어떤가요?**
dsh는 compaction(컨텍스트 오버플로우 복구), guard(타임아웃), interaction(승인) 등의 메커니즘을 가지고 있지만, 복잡한 시나리오의 실패 복구는 아직 발전하는 중입니다. 프로덕션 환경 권장사항: ① guard 타임아웃을 설정해 멈춤을 방지; ② 사람의 승인을 설정해 오작동을 방지; ③ 긴 작업은 단계별로 검증하고, "한 번에 전부 실행한 후 확인"하지 마세요. 구체적인 설정은 제8장 8.5절 보안 모델을 참고하세요.

## 확장 사례(2차, 세 가지 기능 영역)

> 전체 실행 리포트는 [case-expansion-report.md](./case-expansion-report.md) 참고, 산출물은 `docs/assets/`에 있습니다. 전부 합성 데이터입니다.

### 사례 C: HTML 파싱(Web 프론트엔드, 약 3분 18초)

**작업**: 표+폼+차트가 포함된 합성 HTML을 주고, 서드파티 의존성 없이 표를 추출해 CSV로 출력하는 파싱 스크립트를 작성.

**dsh의 성과**:
- **의존성 없음의 트레이드오프**: BeautifulSoup 대신 표준 라이브러리 `html.parser`를 능동적으로 선택
- **견고성**: 표 중첩 깊이 카운팅을 구현해 범위 초과를 방지
- **경로 독립성**: `__file__`로 입력을 위치 확인, 실행 디렉터리에 의존하지 않음

산출물: [case-c-parser.py](./assets/case-c-parser.py) ｜ 검증: 9행×7열 CSV 출력, 원본 표와 필드별로 일치

### 사례 D: 코드 리팩터링(소프트웨어 엔지니어링, 약 4분 37초)

**작업**: 약 200줄의 절차형 주문 스크립트(중복 코드 `calc_order_total` / `calc_order_total_v2` 포함)를 OOP + 책임 분리로 리팩터링, 동작 일치, 테스트 검증.

**dsh의 성과**:
- **정확한 중복 식별**: 동일한 로직 두 개를 `Order.total()`이라는 단일 진입점으로 병합
- **SOLID 설계**: Product/Customer/Order(모델) + OrderProcessor(조회) + ReportGenerator(리포트)
- **하위 호환성**: 모듈 레벨 함수 인터페이스를 유지해 바로 교체 가능
- **테스트 깊이**: 17/17 PASS —— 함수 반환값만 비교하는 게 아니라 **스크립트 레벨 전체 실행 산출물**(report.txt / orders.json)도 비교
- **샌드박스 인식**: `tempfile.mkdtemp`가 샌드박스에서 0700 ACL로 쓸 수 없음을 발견하고 능동적으로 방안 변경

산출물: [case-d-orders_refactored.py](./assets/case-d-orders_refactored.py) + [case-d-test_refactor.py](./assets/case-d-test_refactor.py) ｜ 검증: **17/17 PASS**

### 사례 E: API 문서 생성(문서, 약 1분 04초)

**작업**: 함수 8개가 포함된 Python 모듈에 완전한 Markdown API 문서 생성(파라미터 표/반환값/예외/예시/경계).

**dsh의 성과**:
- **계약 차이 식별**: "문서 선언"과 "코드 구현"의 차이를 능동적으로 발견(예: `user_id` 문자 집합이 강제 검증되지 않음), 경계 섹션에 있는 그대로 작성
- **방어적 문서화**: 각 함수마다 호출 함정을 표시(음수 limit, 빈 updates의 동작)
- **ReadTheDocs 스타일**: 423줄, 함수 8개 전체 커버, doctest 스타일 예시 포함

산출물: [case-e-api.md](./assets/case-e-api.md)

### 2차 사례 특징

| 항목 | 성과 |
|---|---|
| 영역 간 능력 | ✅ Web/엔지니어링/문서 세 가지 작업 모두 폐루프 완성 |
| 엔지니어링 인식 | ✅ 의존성 없음 트레이드오프, 샌드박스 인식, 하위 호환성, 계약 차이 식별 |
| 검증 습관 | ✅ 모든 사례에서 실행 검증(스크립트 레벨 산출물 비교 포함) |
| 소요 시간 | 사례당 1-5분, 복잡도가 높을수록 더 걸림 |

**요약**: dsh는 "코드를 작성하고 + 검증해야 하는" 엔지니어링 작업에서 안정적인 성과를 보이며, **트레이드오프(의존성/호환성/보안)를 판단할 줄 압니다** —— 이것이 agent가 "답할 수 있음"에서 "일을 해낼 수 있음"으로 넘어가는 분기점입니다.
