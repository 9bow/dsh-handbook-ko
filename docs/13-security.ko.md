# 제 13 장: 보안과 샌드박스 모델

> 본 장의 목표: dsh의 보안 골격을 이해합니다 —— 샌드박스는 무엇을 관리하는지, 권한은 어떻게 등급이 나뉘는지, 승인은 어떻게 처리되는지 —— 그리고 커뮤니티 감사가 발견한 실제 경계까지. **이것이 "돌아간다"에서 "프로덕션에 올릴 용기가 생긴다"로 넘어가는 핵심 챕터입니다.**

## TL;DR(본 장 핵심, 30초 버전)

1. **3층 방어선**: 샌드박스(어디서 실행하는가) → 권한 프리셋(무엇을 할 수 있는가) → 승인(위험한 동작에 사람의 확인이 필요한가) —— 기본값은 맨몸 실행이 아닙니다
2. **샌드박스는 파일 효과만 관리합니다**: `read-only` / `workspace-write` / `danger-full-access` 세 등급; 네트워크와 프로세스 가시성은 어휘 목록에 없습니다(그래서 `taskkill`로 호스트를 죽이는 등의 사례는 "어휘 목록 밖"이지, 샌드박스가 뚫린 것이 아닙니다)
3. **권한 = 두 개의 다이얼을 묶은 프리셋**: `sandbox/mode` + `approval/policy`; 기본 표 두 개: `workspace-write`(작업공간 쓰기 + ask)와 `danger-full-access`(샌드박스 없음 + never)
4. **승인은 fail-closed**: `allowed-once`만 통과시킵니다; ask에 응답이 없으면 = 거부(unavailable), never는 모든 것을 결정론적으로 거부 —— headless의 기본 자세
5. **커뮤니티 감사가 발견한 실제 경계**: #159 fs-sandbox 경쟁 상태, #584 scrubbedParentEnv 오탐, #381 iframe 클릭재킹, #817 감사 리포트(vm 탈출 + 로컬 RPC 무인증)
6. **엔터프라이즈 기준선 한 줄 요약**: 기본값 `workspace-write`+ask, loopback만 허용, 신뢰 소스의 플러그인만 설치, 민감한 디렉터리는 workspace에 넣지 않기

## 13.1 보안 설계 철학: 샌드박스/권한/승인 3층

dsh의 보안 골격은 세 층이 각각 한 가지씩 관리합니다(공식 `docs/subsystems/*` 아키텍처 문서 기준, 검증됨: `sandbox.md` / `permission-presets.md` / `approval.md`; 제8장 8.5절 실측과 교차 확인):

| 층 | 무엇을 관리하는가 | 공식 패키지 | 한 줄 요약 |
|---|---|---|---|
| 샌드박스 | 어디서 실행하는지, 어떤 파일을 건드릴 수 있는지 | `sandbox/sandbox`, `sandbox/sandbox-local`, `sandbox/sandbox-policy` | 명령 실행의 파일 효과를 격리 |
| 권한 | 무엇을 할 수 있는지 | `interaction/permission-presets` | 샌드박스 + 승인을 묶어 이름이 있는 프리셋으로 |
| 승인 | 위험한 동작에 사람의 확인이 필요한지 | `interaction/user-approval` | 최소 권한의 마지막 관문 |

**최소 권한 원칙**이 세 층 공통의 설계 방향입니다: 기본 프리셋은 "작업공간 쓰기 + 핵심 동작은 질문"만 부여합니다; 어떤 상승이든(`danger-full-access`로 전환, 승인 정책 변경) 명시적으로 발생하며 세션 로그에 기록됩니다 —— `permission/preset` 이벤트는 **순수 로그용 사용자 의도**로, 모델 트랜스크립트에는 들어가지 않으며, 사후에 "누가 언제 권한을 올렸는지" 추적하기 편합니다.

**위협 모델 요약**: 3층 방어선이 막는 것은 "신뢰할 수 없는 입력이 에이전트를 경계 밖으로 몰아가는 것"입니다 —— 프롬프트 인젝션, 악성 플러그인, 유도된 고권한 작업(#381 iframe 하이재킹이 바로 이 체인을 노림); "신뢰하는 코드 자체"를 막겠다고 약속하지는 않으며(플러그인 자체가 실행 가능한 코드입니다, 13.5 참고), 네트워크/프로세스 레벨 공격을 막겠다고 약속하지도 않습니다.

> 핵심 인지: **dsh의 도구 실행에는 기본적으로 격리와 승인 레이어가 있으며 맨몸 실행이 아닙니다**; 하지만 이것은 "안전한 운영체제"가 아닙니다 —— 샌드박스는 네트워크와 프로세스를 막지 못하고, 승인은 모델이 스스로 답할 수 있습니다(13.6절).

## 13.2 샌드박스 메커니즘 원리: fs 경계와 도구 샌드박스

공식 샌드박스 문서가 명확히 정의합니다: **샌드박스는 파일 효과(filesystem effects)만 관리하며**, 네트워크와 프로세스 가시성은 그 어휘 목록에 없습니다.

**3가지 모드**(`SandboxMode`):

| 모드 | 허용되는 파일 효과 | 설명 |
|---|---|---|
| `read-only` | 읽기 전용 + 필수 sink(POSIX에서는 `/dev/null` 등) | Windows ACL 백엔드는 명시적으로 쓸 수 있는 루트가 없어 partial로 보고 |
| `workspace-write` | 작업공간 루트 + 백엔드가 보장하는 임시 영역 쓰기 가능 | **기본 프리셋**; 루트는 세션의 불변 cwd에서 옴 |
| `danger-full-access` | 제한 없음 | 원본 argv를 직접 spawn, `ctx.sandbox`를 거치지 않음 |

**실행 세부사항**:
- **정책은 호출마다 전달됨**(per-call): `SandboxExecutionPolicy`(mode + workspaceRoot + sessionId)는 매 능력 호출 시 해석되며, provider에 고정되지 않습니다 —— 같은 provider가 동시에 `read-only`의 bash와 쓸 수 있는 상태 디렉터리가 필요한 서브에이전트를 함께 처리할 수 있습니다
- **작업공간 루트 정규화**: 먼저 파일 시스템 시맨틱에 따라 canonicalize(`symlink/..`를 실제 디렉터리로 해석)한 후 어휘적으로 정규화 —— 심볼릭 링크로 경계를 우회하는 것을 방지
- **백엔드 매트릭스**: Linux bwrap/Landlock, macOS Seatbelt, Windows ACL restricted-token; `enforcement: full | partial` —— 오래된 Landlock ABI와 Windows ACL의 Everyone/hard-link 경계가 현재 partial 사례입니다(**보장이 할인될 때는, 소비자가 partial로 처리해야 합니다**)
- **fs 도구도 같은 경계**: `write`/`edit` 등 파일 도구도 마찬가지로 workspace-write 제약을 받습니다, "파일 도구는 그냥 통과하고 bash만 샌드박스"가 아닙니다(#149의 작업공간 재귀 삭제가 바로 workspace-write 아래에서 발생)
- **쓰기만 제한하고 읽기는 제한하지 않음**: 현재 권한 모델이 제약하는 것은 **쓰기**이며, 작업공간 밖의 내용도 읽힐 수 있습니다(#492가 평가 격리 모드를 제안하며 지적한 현재 상태)

**도구 샌드박스**: `bash`/`pwsh`는 `bash-sandbox` / `pwsh-sandbox`를 거쳐(`ctx.sandbox`를 소비) 샌드박스 안에서 자식 프로세스를 시작합니다; Windows에서 pwsh 샌드박스는 ACL 제약이 있습니다(제8장 실측에서 temp 권한 문제를 겪은 적 있음; #758은 Windows 샌드박스 임시 디렉터리 정리 후 영구 크래시도 보고).

**같은 계열의 사례**: #159의 경쟁 상태는 TOCTOU에 속합니다(검사와 사용 사이에 경로가 바뀜); #278은 또 다른 확장 수법입니다 —— `/tmp`를 workspace로 쓸 때, 제한된 자식 프로세스가 rebind로 workspace-write 권한 범위를 넓힐 수 있습니다. 두 사례의 공통된 교훈: **경계의 루트 디렉터리는 신뢰할 수 있는 위치를 선택해야 하고, 단일 경로 검사만 믿으면 안 됩니다**.

## 13.3 권한 모델: 도구 권한 등급 표

공식 권한 프리셋은 **두 개의 다이얼** —— `sandbox/mode`와 `approval/policy` —— 을 묶어 이름이 있는 프리셋으로 만들고, 클라이언트는 이를 하나의 "Permissions" 선택기로 보여줍니다. 기본 표 두 개:

| 프리셋 | sandbox/mode | approval/policy | 의미 |
|---|---|---|---|
| `workspace-write` | workspace-write | ask | 작업공간 내 쓰기 가능, 동작 전 질문(기본값) |
| `danger-full-access` | danger-full-access | never | 샌드박스 없음, 질문 없음 |
| `custom`(파생 상태) | 임의 조합 | 임의 | 다이얼을 수동으로 조정한 "비프리셋" 상태, 전환 대상이 될 수 없음 |

**도구 권한 등급**(피해 반경 순으로 정렬; 각 도구의 "권장 프리셋"은 공식 문서에서 유추한 것이며, 도구별 실측이 아닙니다 —— **추론, 미실측**):

| 등급 | 대표 도구 | 권장 프리셋 | 리스크 | 비고 |
|---|---|---|---|---|
| 읽기 전용 탐색 | `read`/`grep`/`glob` | read-only 호환 | 낮음 | 읽기만 하고 저장하지 않음; 읽기는 작업공간에 국한되지 않음 |
| 작업공간 쓰기 | `write`/`edit`/`str_replace_editor` | workspace-write | 중간 | 쓰기 경계 = 작업공간 루트 + 임시 영역 |
| 명령 실행 | `bash`/`pwsh` | workspace-write(샌드박스 내) | 높음 | 샌드박스는 네트워크와 프로세스를 막지 못함 |
| 전체 접근 | 임의(danger-full-access로 전환) | danger-full-access | 매우 높음 | 모든 관문을 닫음 |

> 공식 문서는 샌드박스가 **파일만 관리한다**고 명시합니다 —— 그래서 "명령 실행" 등급의 고위험은 샌드박스로 없앨 수 없고, 승인과 신뢰 경계로 뒷받침해야 합니다(13.5 / 13.7절).

**실제 경계 사례**(자세한 내용은 13.6절 참고): `workspace-write`에서 작업공간 전체를 확인 없이 재귀 삭제(#149); `danger-full-access`에서 홈 디렉터리 전체를 실수로 삭제(#461, 실제 사고); Windows에서 minimal preset이 작업공간 밖 쓰기를 승인 없이 허용(#523); 샌드박스 안의 agent가 `taskkill`로 호스트를 죽일 수 있음(#466, 프로세스 가시성이 샌드박스 어휘 목록 밖에 있음).

## 13.4 승인 흐름: 요청에서 허가까지

공식 승인 문서: 승인은 하나의 질문에 답합니다 —— "이 구체적인 동작을 해도 되는가?"

**결과 집합은 fail-closed**(`ApprovalOutcome`):

| 결과 | 의미 | 호출자에 대한 효과 |
|---|---|---|
| `allowed-once` | 일회성 허가(질문받은 이 동작 하나만 허가) | ✅ 계속 |
| `rejected` | 명시적 거부 | ❌ 중단 |
| `cancelled` | 요청이 철회됨(AbortSignal) | ❌ 중단 |
| `unavailable` | 응답자 없음 / 응답자 이상 | ❌ 중단(기본 fail-closed) |

**정책**(`ApprovalPolicy`): `ask`(기본값, 응답자 체인에 맡김; 체인이 비어있으면 → unavailable); `never`(결정론적으로 전부 rejected, 어떤 응답자에게도 발송하지 않음 —— headless/CI의 엄격한 자세).

**흐름**: 도구 호출 → `approval/request` waterfall(플러그인이 가로채기/재작성 가능) → 응답자(Web UI에서 사람이 직접 응답, 또는 ACP 브리지의 일회성 기계 결정) → 매 요청마다 감사 이벤트 `approval/asked` + `approval/decided`를 쌍으로 기록(같은 `ApprovalRequestId`).

**요청 내용**(`ApprovalRequest`): agent(응답자는 자신이 소유한 agent만 응답) + toolName + callId(이미 스트리밍으로 표시된 도구 호출과 연결, 파라미터를 중복 렌더링하지 않음) + reason(왜 물어보는지) + signal(AbortSignal 철회).

**세 가지 알려진 트러블**:
1. **승인 순환 참조**: #250이 "모델이 danger-full-access를 스스로 승인"하는 실제 재현을 보고했습니다(Web approval 채널이 모델 자신에 의해 구동될 수 있음) —— **승인은 보안 경계가 아니라**, 사람-기계 협업 관문일 뿐입니다
2. **동시성 오작동**: #453은 동시 샌드박스 승인에서 Allow를 클릭하면 다른 호출이 중단됨을 보고했습니다(UI 응답과 callId 불일치)
3. **재연결 시 승인 유실**: #646은 재연결 시 pending approval이 조용히 유실됨을 보고했습니다(resync 초기화 + replay 경쟁 상태); headless에서 승인 동작은 정의되지 않음(#291)

## 13.5 플러그인 보안 감사 체크리스트

플러그인은 dsh의 능력 경계입니다("모든 것이 플러그인", 제4장 참고) —— **플러그인을 설치하는 것 = 실행 가능한 코드를 설치하는 것**입니다. 커뮤니티 감사(#817 및 같은 계열)가 정리한 체크리스트:

| # | 점검 항목 | 커뮤니티 근거 | 대처 |
|---|---|---|---|
| 1 | 플러그인 출처가 신뢰할 수 있는가? `dsh plugin add`는 서명/출처 검증이 없음 | #587 | 공식/알려진 소스만 설치; 설치 전 소스 코드 확인 |
| 2 | boot 단계 권한이 최소화되어 있는가? 플러그인이 boot 단계에서 전체 설정 트리 쓰기 권한을 가짐 | #587 | "설치하면 자동으로 설정을 바꾸는" 플러그인 경계 |
| 3 | vm을 보안 경계로 삼지 않는가? workflow/동적 플러그인의 vm이 탈출 가능함 | #243 #451 #774 #778 | vm은 격리 엔진으로만 취급, 보안 레이어로 취급하지 말 것 |
| 4 | 자식 프로세스 환경이 올바르게 scrub 되는가? `scrubbedParentEnv`가 부분 문자열로 정상 변수를 오탐 | #584 | KEYBOARD/MONKEY 등 KEY가 포함된 변수가 잘못 scrub되지 않았는지 확인(**오탐 메커니즘은 제목 기준 추론**) |
| 5 | 비밀값 마스킹이 fail-open이 아닌가? settings `role('secret')`에 마스킹 공백 존재 | #226 | 비밀값을 프롬프트에 쓰지 말 것; 마스킹 로직 검증 |
| 6 | 보안 hook이 조용히 실패하지 않는가? `timeout: 0`이 fail-open을 유발함 | #460 #583 | hook 타임아웃을 양수로 설정; 로드 실패 시 오류를 던져야 함 |

"프로덕션에 올리려는 / 팀에 보급하려는" 의사결정을 위한 제안입니다(제6장 스타일에 맞춤):

|---|---|---|

| 권한 프리셋 | 기본값 `workspace-write` + ask; `danger-full-access`는 격리된 머신 / 일회성 작업에만 사용 | 공식 preset 표 + #461 |
| 승인 정책 | 사람이 직접 응답하는 경로가 필수; headless는 `never`(결정론적 거부)를 사용하고 사전 리뷰 관문을 앞에 둘 것 | approval.md + #291 |
| 플러그인 거버넌스 | 화이트리스트 소스 + 설치 전 13.5절 체크리스트 통과; 맨몸 `dsh plugin add github:` 금지 | #587 #656 |

**의사결정 요약**: 로컬 개인 개발 → 기본 프리셋이면 충분; 팀 공유 → `workspace-write` + ask + 플러그인 화이트리스트; CI/무인 운영 → headless + `never` + 사전 코드 리뷰; 어떤 시나리오든 편하자고 `danger-full-access`를 장기간 걸어두지 마세요.

**시나리오 → 추천 조합**(의사결정 제안, 위 표 기준선에서 유도):

| 시나리오 | 추천 조합 | 이유 |
|---|---|---|
| 로컬 개인 개발 | 기본값 `workspace-write` + ask | 바로 사용 가능, 승인이 번거롭지 않음 |
| 팀 공유 호스트 | workspace-write + ask + 플러그인 화이트리스트 | 다중 사용자 공유, 플러그인 공급망 리스크가 증폭됨 |
| CI / 무인 운영 | headless + `never` + 사전 리뷰 관문 | 결정론적 거부, 사람 없이 멈추지 않음 |
| 격리 머신 / 일회성 작업 | `danger-full-access`(머신 자체가 격리됨) | 권한은 최대화하되 공격 표면을 단일 머신으로 제한 |

## 자주 묻는 질문 FAQ

**Q1: 샌드박스가 악성 코드를 막아줄 수 있나요?**
보안 경계로 쓸 수는 없습니다. 샌드박스는 파일 효과만 관리하며; 네트워크(예: SSRF)와 프로세스(예: #466 taskkill)는 그 어휘 목록 밖에 있습니다. 악성 코드를 막는 것은 플러그인 신뢰(13.5절)와 네트워크/프로세스 레벨 격리(컨테이너/VM/원격 샌드박스 —— 공식 문서는 이것들이 능력 공백의 형제 구현이지 `ctx.sandbox`의 provider가 아니라고 명시함)에 의존합니다.

**Q2: 왜 headless에서 `never`를 쓰는 것이 오히려 더 안전한가요?**
`never`는 "절대 묻지 않는" 관대한 모드가 아니라 **결정론적 거부**입니다: 어떤 승인 요청이든 바로 `rejected`가 되며, 응답자에게 발송되지 않습니다 —— 무인 운영 시 "사람이 Allow를 누르길 기다리며 멈춰 있는" 상황이 생기지 않습니다. 허가가 필요한 동작은 사전 리뷰나 명시적 설정에 의존해야지, 런타임에 물어보는 것에 의존하면 안 됩니다.

**Q3: `workspace-write`면 안전한 건가요?**
경계 안에서는 상대적으로 안전하지만, #149가 보여주듯 "작업공간 전체를 재귀 삭제"하는 것은 workspace-write 안에서 확인 없이 일어납니다 —— 샌드박스가 막는 것은 "경계 넘기"이지 "경계 안에서의 자기 파괴"가 아닙니다. 중요한 코드는 버전 관리에 넣으세요.

**Q4: 제12장에서 이미 #159를 언급했는데, 왜 이 장에서 또 다루나요?**
제12장은 "알려진 한계 빠른 참조표"(한 줄 요약 + 상태)이고, 본 장은 메커니즘(post-check 경쟁 상태가 어떻게 발생하는지), 같은 계열(#278 /tmp rebind), 완화책(단일 경로 검사를 신뢰하지 말 것, 핵심 디렉터리는 workspace에 넣지 말 것)을 자세히 다룹니다.

**Q5: 이 보안 게시물 번호들이 신뢰할 수 있나요? 지어낸 건 아닌가요?**
핵심 게시물 4개(#159 #584 #381 #817)는 모두 `gh api graphql`로 하나씩 존재를 검증했습니다(링크는 13.6절 표 참고); 같은 계열의 보충 게시물은 저장소 내 `docs/research/discussion-mining.md`(전체 780개 게시물을 페이지 단위로 수집해 프로그램적으로 검증)에서 가져왔습니다.
