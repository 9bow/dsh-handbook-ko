# 제 14 장: 캐시와 비용 엔지니어링

> 본 장의 목표: "저렴함"을 감이 아니라 엔지니어링으로 만듭니다 —— 대화 캐시 메커니즘, 적중률 실측과 최적화, 비용 모델, 추론 강도 연계, 실제 작업 예산, 그리고 매 토큰이 어디에 쓰이는지 "보는" 방법.

## TL;DR(본 장 핵심, 30초 버전)

1. **캐시가 비용의 첫 번째 변수입니다**: DeepSeek context cache는 반복되는 입력에 **96.8% 할인(Flash) / 96.7% 할인(Pro)**을 적용합니다(오프피크 시간대, 2026-08-16부터 피크/오프피크 요금제 시작) —— Agent 워크로드는 입력 비중이 높아서, 적중률이 비용 규모를 직접 결정합니다
2. **피크/오프피크 요금제가 가장 큰 새로운 레버입니다**: 피크 시간은 UTC 01:00-04:00 + 06:00-10:00(한국시간 오전 10:00-13:00 + 15:00-19:00, 거의 평일 근무시간 전체를 덮음) —— 일상적인 코딩 시간은 거의 전부 2배 가격 구간에 들어갑니다; 긴 작업(배치 리팩터링/테스트/agent 긴 작업)을 저녁이나 아침 일찍으로 옮기면 청구서가 **바로 절반**이 됩니다 —— 적중률과 **곱셈으로 누적**되며, 설정을 바꿀 필요도 없습니다(14.1)
3. **핸드북 실측 적중률 97%**: 세션 연속성 + 안정적인 도구 스키마 + Agent 다단계 워크로드 특성(제5장 5.1.1); 커뮤니티의 긴 실행 실측은 99.7%까지 달성([#560](https://github.com/deepseek-ai/deepseek-harness/discussions/560))
4. **적중률 3원칙**: 세션 연속성(자주 새로 만들지 않기), 접두사 안정성(설정을 자주 바꾸지 않기), 끊김 최소화(검수 기준을 한 번에 명확히 쓰기)
5. **두 개의 독립된 레버**: 추론 강도는 "사고 토큰 양"을 관리하고, 캐시는 "입력 단가"를 관리하며, 서로 누적됩니다 —— `low` 등급 + 고적중 = 가장 저렴한 조합
6. **비용은 눈에 보여야 합니다**: 세션 통계 행에서 캐시 적중 %를 확인; 라운드별 토큰 표시는 공식이 아직 구현하지 않았으며([#735](https://github.com/deepseek-ai/deepseek-harness/discussions/735)), 우선 통계 행 + 커뮤니티 cost-tracker 플러그인을 쓰거나, 설치 없이 바로 session.jsonl.zstd를 읽는 방법이 있습니다(14.7)

## 14.1 대화 캐시 메커니즘 원리

DeepSeek API의 **context cache**(프롬프트 캐시): 반복/유사한 입력 토큰은 전체 가격이 아니라 **캐시 가격**으로 과금됩니다. dsh의 매 모델 요청의 입력 = 시스템 프롬프트 + 스킬 카탈로그 + 대화 이력 + 도구 스키마(제8장 8.3), **그중 변하지 않는 접두사 부분이 바로 캐시의 자연스러운 후보**입니다 —— 이것이 Agent 워크로드의 캐시 잠재력이 일반 채팅보다 훨씬 높은 이유입니다.

**과금 규칙**(**2026-08-16 16:00 UTC부터 피크/오프피크 요금제 시행**, 공식 [가격 페이지](https://api-docs.deepseek.com/quick_start/pricing); 제5장 5.1.1은 여전히 피크/오프피크 요금제 이전의 옛 통일 가격표이며, 기준은 본 장을 따릅니다):

| 모델 | 캐시 적중 | 미적중 | 출력 |
|---|---|---|---|
| v4-flash 오프피크 | $0.007 | $0.22 | $0.66 |
| v4-flash 피크 | $0.014 | $0.44 | $1.32 |
| v4-pro 오프피크 | $0.022 | $0.66 | $1.98 |
| v4-pro 피크 | $0.044 | $1.32 | $3.96 |

(단위: 미국 달러/백만 토큰)

**할인율 변화(구 → 신)** —— 14.3의 3원칙 방향은 여전히 성립하지만, "캐시가 입력 단가를 관리한다"는 레버는 짧아졌습니다:

| | 구 요금표(통일 가격) | 신 요금표(오프피크) |
|---|---|---|
| Flash 적중 할인율 | 98% | **96.8%** |
| Pro 적중 할인율 | 99.2% | **96.7%** |
| Flash 미적중/적중 배율 | 50배 | **31배** |
| Pro 미적중/적중 배율 | 120배 | **30배** |

동시에 **출력 가격 = 미적중 가격의 3배**입니다(구 요금표는 2배) —— **출력 비중이 큰 작업에서는 캐시 최적화로 회수할 수 있는 비율이 구 요금표로 계산한 것보다 작습니다**(출력은 캐시 할인을 받지 못하고, 상대적으로 입력 가격의 비중이 상승했기 때문).

**피크/오프피크 요금제(2026-08-16 16:00 UTC부터)**:

- **피크 시간**: UTC **01:00-04:00** + **06:00-10:00**; 나머지는 **오프피크**이며, 오프피크 가격은 정확히 피크의 절반입니다(적중/미적중/출력 세 등급이 함께 절반이 됨)
- **한국시간(KST) 기준** 피크 시간 = **오전 10:00-13:00** + **오후 15:00-19:00** —— 한국의 평일 근무시간과 거의 정확히 겹치며, 점심시간만 벗어나 있습니다
- **국내(중국) 사용자 기준**: 일상적인 코딩 시간은 거의 전부 2배 가격 구간에 들어갑니다; **긴 작업**(배치 리팩터링, 테스트 실행, agent 긴 작업)을 **저녁이나 아침 8시 이전**으로 옮기면 청구서가 바로 **절반**이 됩니다
- 이것은 **100%의 가격 차이**로, 14.3의 어떤 최적화보다도 폭이 크며, **어떤 설정 변경도 필요 없습니다**
- 적중률과는 **곱셈 관계**이지 덧셈이 아닙니다: 오프피크는 세 등급을 함께 절반으로 낮추며, 14.3의 최적화와 충돌하지 않고 누적 가능합니다(14.3절 끝 참고)

**매 요청의 입력 구조**(제8장 8.3)가 어떤 토큰이 적중할 수 있는지를 결정합니다:

```text
시스템 프롬프트(안정) + 스킬 카탈로그(안정) + 대화 이력(증분) + 도구 스키마(안정) + 이번 라운드 메시지(증분)
      └────────────── 캐시 적중 영역(반복) ──────────────┘   └── 미적중 영역(새 증분) ──┘
```

**적중 영역이 클수록, 증분이 작을수록 → 적중률이 높아집니다**. 이 구조를 이해하면, 14.3의 세 가지 최적화 레버는 본질적으로 모두 "적중 영역을 크게 만드는" 것입니다.

**캐시는 비용만 절약하는 게 아니라 속도도 높입니다**: 콜드 스타트 첫 라운드는 컨텍스트 주입을 포함해 약 110초, 핫 캐시는 약 1초입니다(제1장 실측) —— 적중 시 첫 토큰 시간이 자릿수 단위로 단축됩니다.

> **엄격한 접두사 캐시 규칙(커뮤니티 분석, #1052 weijiafu14, 공식 문서 [kv_cache](https://api-docs.deepseek.com/guides/kv_cache/))**: DeepSeek은 **엄격한 접두사 캐시**입니다 —— 접두사 단위는 **사용자 입력이 끝나거나 모델 출력이 끝나는 등의 지점에서 영속화**됩니다; 다음 요청은 "완전히 일치하는" 접두사만 적중할 수 있습니다. 핵심 추론:
> - **도구 결과는 필연적으로 한 번은 miss합니다**: 도구 결과는 "직전 라운드 모델 출력" 이후에야 추가되는 것이라, 다음 요청에 처음 들어갈 때는 **반드시 새로운 접미사이며 반드시 한 번은 miss**합니다 —— 원문을 전달하든 압축된 미리보기를 전달하든 상관없습니다(이것은 자르는 방식과 무관합니다).
> - **"자르면 캐시를 피할 수 있다"는 오해입니다**: 자르기가 결정론적이기만 하면(같은 입력에 같은 출력) 이후 재생되는 것은 동일한 바이트이므로, 기존 접두사는 그대로 적중합니다; miss하는 것은 처음 나타나는 압축 결과와, 이후 능동적으로 artifact를 읽어 추가한 내용뿐입니다. **압축 도구는 DeepSeek 캐시를 우회하지 않으며, 오히려 "필연적으로 처음 miss하는" 도구 결과를 줄여줍니다**(#1052 weijiafu14 실측: 원본 도구 출력 42,299자 → 압축 영속화 7,885자, 이후 derive/replay 해시 일치).
> - **대가에 대한 안내(#1052 fnsii + weijiafu14)**: 캐시 자체는 best-effort이며 공식은 100% 적중을 보장하지 않습니다(weijiafu14가 공식 설명을 인용); 컨텍스트 접두사를 전혀 유지하지 않으면(예: 매 라운드 재작성/이력 초기화, 새 세션으로 전환해 접두사를 전부 버림) 캐시를 전혀 적중할 수 없어, 새 입력으로 전체 가격을 지불하는 것과 같습니다(fnsii). **한도에 거의 도달했을 때는 summary 압축을 먼저 하고 이어가는 것을 우선하세요**(접두사 요약을 유지), 접두사를 전부 버리고 바로 새 세션을 여는 것보다 낫습니다(fnsii의 제안).

## 14.2 적중률 실측: 97%는 어떻게 나왔나

핸드북은 **실제 dsh 세션 통계**에서 캐시 적중률이 **97%에 달할 수 있음**을 실측했습니다(제5장 5.1.1). 왜 dsh의 적중률이 특히 높은가:

| 이유 | 설명 |
|---|---|
| 세션 연속성 | 같은 세션에서 여러 라운드 대화 시, 시스템 프롬프트/스킬 카탈로그/이력이 반복됨 → 적중 |
| 안정적인 도구 스키마 | 매 단계 요청마다 동일한 도구 정의를 전달함 → 적중 |
| Agent 워크로드 특성 | 다단계 도구 체인이 반복적으로 동일한 컨텍스트를 전달함 → 적중률이 자연히 높음 |

**경계(솔직한 버전)**: 97%는 "대화 패턴 반복"에 의존합니다 —— **완전히 새로운 작업/콜드 스타트 시나리오에서는 눈에 띄게 낮아집니다**(제12장 12.5). 커뮤니티의 긴 실행 실측은 **99.7%**까지 달성합니다([#560](https://github.com/deepseek-ai/deepseek-harness/discussions/560)), "세션이 길수록 적중률이 높아진다"는 것을 뒷받침합니다.

**실측 방법**: Web UI 하단 세션 통계 행에서 "캐시 적중 %"를 확인(제6장 6.6); 비교 기준은 5.1.1의 "50단계 도구 체인 작업, 240만 입력 토큰"입니다 —— 이는 입력 규모의 전형적인 표본입니다.

> **기준 주의사항(#1234 커뮤니티 보충)**: Harness 인터페이스에 표시되는 "캐시 적중 %"는 **대화 내** 기준입니다 —— 현재 세션의 요청만 통계에 잡습니다. 같은 시간대에 여러 대화를 열었다면, 다른 대화의 적중률이 낮을 때 **다중 대화 전체/백엔드 기준**이 낮아집니다(커뮤니티 실측 대조: 백엔드/전체 약 94.5% vs 인터페이스(대화 내) 98%, [#1234](https://github.com/deepseek-ai/deepseek-harness/discussions/1234)). **적중률을 측정할 때는 먼저 기준을 명확히 하세요**: 대화 내(인터페이스 통계 행)인지 다중 대화 전체(백엔드/API 측)인지; 적중률 비교는 같은 기준 안에서만 의미가 있습니다.

> **기준 주의사항 2(피크/오프피크 요금제, #45 작성자 실측 경험)**: 2026-08-16부터 피크/오프피크 요금제가 시행된 후, **피크/오프피크 경계를 넘나드는 세션**에서는, 같은 접두사가 경계 전후로 다른 단가로 과금됩니다 —— 비용 대조 실험을 할 때는(예: 14.4의 비용 모델, 14.2의 적중률 실측), **경계를 넘는 세션과 넘지 않는 세션은 금액으로 직접 비교할 수 없고, 토큰으로만 비교할 수 있습니다**. #45 작성자가 실측에서 겪은 트러블: 두 그룹의 데이터를 재계산할 때야 시간 분포가 다르다는 것을 발견했고, 금액으로 비교하면 잘못된 결론을 내리게 됩니다.

| 지표 | 어디서 보는가 | 적중 시의 양상 |
|---|---|---|
| 캐시 적중 % | 세션 통계 행(Web UI 하단) | 높은 수준에서 안정적(긴 세션 97%+) |
| 첫 토큰 | 매 라운드 종료 행 | 10초+ 수준에서 1초 미만으로 자릿수 단위로 떨어짐(제6장 FAQ Q4) |
| 총 토큰 | 세션 개요 | 증분이 작음 = 적중 영역이 커지고 있음(14.1 구조) |

## 14.3 적중률 최적화 실천

세 가지 레버를 가성비 순으로 정렬합니다:

| 레버 | 방법 | 원리 |
|---|---|---|
| **세션 연속성** | 긴 작업은 세션 연속성을 유지, 자주 새 세션을 만들지 않기; 배치 작업은 같은 세션/같은 접두사에 두기 | 이력 메시지가 반복됨 → 적중 |
| **안정적인 프롬프트** | 시스템 프롬프트/스킬 카탈로그 등 접두사를 안정적으로 유지, 설정을 자주 바꾸지 않기; 도구 스키마를 불변으로 | 접두사가 일관됨 → 적중 |
| **끊김 최소화** | 검수 기준을 한 번에 명확히 쓰기(제5장 5.7 / 제10장 사례 시사점), "세션을 다시 열어 컨텍스트를 다시 설명"하는 것을 줄이기 | 접두사 재구축을 피함 → 전체 가격 재시작 방지 |

**실행 점검**: 적중률이 예상보다 낮을 때, 첫 반응은 "접두사가 바뀌었는지" 확인하는 것입니다 —— 설정을 바꿨거나, 강도를 바꿨거나, 스킬 카탈로그를 건드렸으면 모두 캐시를 무효화시킵니다(제6장 6.6 모니터링 행).

**피크/오프피크는 네 번째이자 가장 큰 레버입니다**: 긴 작업(배치 리팩터링, 테스트 실행, agent 긴 작업)을 오프피크로 옮기면(한국시간 저녁이나 아침 8시 이전), 청구서가 바로 **절반**이 됩니다 —— 100%의 가격 차이로, 위 세 가지보다 폭이 크며, 적중률과 **곱셈 관계**입니다(오프피크는 적중/미적중/출력 세 등급을 함께 절반으로 낮춤, 14.1), 3원칙과 누적 가능하며 어떤 설정 변경도 필요 없습니다.

## 14.4 비용 모델: 적중률이 청구서를 어떻게 결정하는가

**비용 모델 요약**(제6장 6.6): `총 비용 ≈ 출력 토큰×출력 가격 + 입력 미적중×미적중 가격 + 입력 적중×적중 가격` —— Agent 워크로드는 입력 비중이 높아서, **캐시 적중률이 비용의 첫 번째 변수**입니다.

14.1의 오프피크 Flash 입력 가격으로 계산해봅니다(**입력 1만 토큰**, 적중률 비교). 산술 예시(90% 적중): `9,000 × $0.007/M + 1,000 × $0.22/M ≈ $0.000283` —— 적중/미적중을 먼저 나눈 후, 각각의 단가를 곱합니다:

| 적중률 | 적중 토큰 | 미적중 토큰 | 입력 비용(Flash 오프피크) | 상대 비용 |
|---|---|---|---|---|
| **90%** | 9,000 | 1,000 | ≈ $0.000283 | 1× |
| 50% | 5,000 | 5,000 | ≈ $0.001135 | ≈ 4.0× |
| **10%** | 1,000 | 9,000 | ≈ $0.001987 | ≈ 7.0× |

100만 입력 토큰으로 확대하면: 90% 적중 ≈ **$0.0283**, 10% 적중 ≈ **$0.199**, 전체 가격 $0.22(오프피크 미적중) —— **거의 자릿수 하나 차이**입니다.

핸드북 실측 규모로 다시 확대하면(5.1.1: 50단계 도구 체인, 240만 입력 토큰): 97% 적중 ≈ **$0.032**, 전체 가격 ≈ **$0.53**, 약 **16배**. 이것이 5.1.1의 "비용이 미적중 가격 기준 예상치보다 훨씬 낮다"는 수치의 출처입니다(참고: 구 요금표에서는 이 배율이 약 20배였는데, 신 요금표는 적중 할인이 줄어들어 16배로 내려갔습니다, 14.1 참고).

> 참고: 이 표는 입력 쪽만 계산한 것입니다 —— 출력 쪽은 14.1의 가격표 참고(출력 = 미적중의 3배이며, 캐시 할인을 받지 못함); 출력 비중이 큰 작업에서는 캐시 최적화의 이득이 입력 비중이 큰 작업보다 작을 것입니다(14.1 할인율 변화).

> **접두사 슬리밍 실측(#45, 데이터와 스크립트는 [sjh9714/dsh-lean](https://github.com/sjh9714/dsh-lean)에 있음)**: 32회 짝지어 실행, 매번 작업의 깨끗한 사본에서 시작해 양쪽 모두 작업에 내장된 테스트 스위트로 산출물을 검증했습니다. 기본 `standard` preset의 접두사는 **8,246개의 미적중 토큰**이며, 그중 약 **3,700개**는 단일 에이전트 세션이 전혀 호출하지 않는 도구(delegation 그룹, goal, jobs)에서 나옵니다 —— 현행 피크/오프피크 요금표 기준, 이 한 번의 접두사가 **전체 청구서의 46%를 차지**합니다(6개 요청 작업, 3회 실행 평균; 구 통일 요금표 기준으로는 52%). 추론: **"접두사 슬리밍"** —— 전혀 쓰지 않는 도구를 덜 걸어두는 것 —— **이 고가치 최적화 방향입니다**, 원본 토큰 수는 저장소에 이미 제출되어 있어 신 요금표로 정확히 재계산할 수 있습니다.

## 14.5 추론 강도 연계: low/high/max 비용 매트릭스

추론 강도는 "사고량"을 관리하며, 캐시와는 **두 개의 직교하는 레버**입니다: 강도는 토큰 총량에, 캐시는 입력 단가에 영향을 주며, 둘은 곱해집니다. 사고 토큰 감소 → 총 토큰 하락(제6장 6.6), 그리고 컨텍스트가 반복되는 부분에 따라 마찬가지로 캐시 할인을 받습니다(추론, 미실측).

| 강도 | 사고 토큰 양 | 상대 비용 | 적용 시나리오(제6장 6.2) | 비용 전략 |
|---|---|---|---|---|
| `low` | 최소 | 최저 | 단순/결정론적 라운드: 파일 조작, 배치, 도구 체인 중 저렴한 단계 | 배치 작업의 기본 강도 |
| `high` | 중간 | 중간 | 일상적인 Agent 작업(기본값) | 품질과 비용의 기본 균형 |
| `max` | 최대 | 최고 | 복잡한 추론, 긴 체인 계획, 디버그 | 단발성 복잡한 작업에는 가능, 배치 루프에는 열지 말 것 |

**연계 포인트**:
- **긴 도구 체인 작업(20-50단계)에서 이득이 가장 큼**: 매 단계 사고 강도 다운그레이드의 누적 효과가 뚜렷함(제6장 FAQ Q2) —— 강도 × 적중률 두 레버가 매 단계마다 동시에 작용
- 단순 라운드에 `low`를 쓰면 품질 차이가 거의 없음; 복잡한 추론에 `low`를 쓰면 핵심 단계를 놓칠 수 있음(제6장 FAQ Q3)
- **누적 예시**(240만 입력 규모 작업, Flash 오프피크 가격): `low` + 97% 적중 ≈ $0.032 이하(사고량이 더 낮아 실제로는 더 적음, 추론, 미실측); `max` + 반복적인 콜드 스타트 ≈ $0.53 이상 —— **같은 작업인데, 두 레버를 전부 켰을 때와 전부 껐을 때 16배+ 차이**
- 참고: `low/high/max`는 본 핸드북이 실측한 게이트웨이(pi-ai/opencode-go) 강도입니다; 기본 deepseek-official 어댑터는 `off/high/max`입니다(제6장 6.2절 참고)

## 14.6 예산 실전: 사례 A 비용 추정

제10장 **사례 A(데이터 품질 분석, 186초)**를 표본으로 예산을 세워봅니다: 도구 체인 `read → write(clean.py) → bash → write(visualize.py) → bash → read → 요약`, 약 6-8단계. 5.1.1 규모로 환산하면(50단계 ≈ 240만 입력 토큰), 사례 A의 입력 규모는 약 **50만 토큰(추론, 미실측)**입니다:

| 시나리오 | 적중률 | 입력 비용(Flash 오프피크, 추정) |
|---|---|---|
| 세션 연속성 + 접두사 안정(권장 방법) | 97% | ≈ **$0.0067** |
| 중간에 새 세션/접두사 변경 | 10% | ≈ $0.099 |
| 극단: 매번 전체 가격 | 0% | $0.11 |

**단계별 분해**(왜 세션 연속성이 비용을 절약하는가) —— 첫 라운드만 콜드 스타트 전체 가격이고, 이후 매 라운드는 "이번 라운드 메시지 + 도구 결과"라는 작은 새 증분만 미적중입니다(추론, 미실측):

| 단계 | 내용 | 입력 토큰(추론, 미실측) | 적중 상태 |
|---|---|---|---|
| 1 | read(sales_data.json) | ~5만 | 콜드 스타트(미적중) |
| 2-6 | write/bash/write/bash/read/요약 | ~45만 | 접두사 적중 영역, 증분 극히 적음 |

**결론**: 3분짜리 실제 작업 하나의 입력 쪽 비용은 **1센트 미만**입니다; 같은 일을 하는 방식이 다르면(세션 연속성 vs 반복적인 콜드 스타트) 비용이 **약 16배** 차이 납니다. 출력 쪽(스크립트 2개 + 요약)의 규모는 입력보다 훨씬 작아, 총 비용은 여전히 센트 단위입니다(추론, 미실측). 이것이 "dsh + V4-Flash 조합의 비용이 Claude 대비 약 1/10~1/30"(제1장 실측)이라는 것의 단일 작업 차원 출처입니다.

## 14.7 측정 방법: 토큰 소비를 보이게 만들기

**현재 상태(있는 것)**:
- Web UI 하단 세션 통계 행: `N 라운드 · M 단계 | LLM Xs · 도구 호출 Ys | 첫 토큰 평균 ...`(제6장 6.3)
- 매 라운드 종료 행: `10:14 · 소요 9분 34초 · 첫 토큰 1.7초 · 79 tok/s`([#735](https://github.com/deepseek-ai/deepseek-harness/discussions/735) 원문 스크린샷)
- 세션 개요에는 총 토큰 통계가 있음; 통계 행에서 "캐시 적중 %"를 볼 수 있음(제6장 6.6) —— **대화 내 기준**이며, 다중 대화 전체 적중률은 다른 저적중 대화에 의해 낮아질 수 있음([#1234](https://github.com/deepseek-ai/deepseek-harness/discussions/1234) 커뮤니티 보충, 14.2 기준 주의사항 참고)

**공백(없는 것)**: **매 라운드의 토큰 수**. 공식 디스커션 [#735](https://github.com/deepseek-ai/deepseek-harness/discussions/735)(2026-08-14 제기, 제목 「【친절한 표시】매 대화 라운드에 이번 라운드의 토큰 소비량을 추가해줬으면 좋겠다」)가 바로 이 요구사항입니다 —— 게시물에서 존재가 확인되었지만, 공식은 아직 구현하지 않았습니다.

**또 다른 공백(#735 댓글 Jianye)**: 매 라운드 표시에 **provider와 model id 식별자**를 포함해달라는 요청(원문 스크린샷의 `xtoken：gpt-5.6-sol` 같은 "provider + modelid" 정보를 사용자가 인터페이스에서 바로 받고 싶어함) —— 같은 요구사항 게시물 아래의 보충 요청입니다.

**커뮤니티 제안(#735 댓글에 이미 반영됨)**: 매 라운드 표시는 **두 개의 숫자**로 나눠야 합니다 —— ① 이번 라운드 총 토큰(대략적인 소비량); ② 이번 라운드 캐시 적중/미적중 토큰(비용 최적화 여지 확인). 총 토큰만 보면 오판할 수 있습니다: 같은 1만 토큰이라도 적중률 90%와 10%는 비용이 7.0배 차이 납니다(14.4 참고).

**과도기 도구**: 커뮤니티 `dsh-plugin-cost-tracker`(제9장 9.5/9.6, 실시간 토큰 비용 추적, 플러그인/MCP 형태) —— 구현 레벨에서는 제4장의 플러그인 확장 포인트를 거쳐, 요청/세션 이벤트에서 usage를 통계 냅니다(추론, 미실측); 또는 세션 로그/API usage 필드로 수동 계산할 수도 있습니다. 제11장은 "캐시 적중률 도구화"가 중기의 주요 흐름이라고 예측합니다(11.2) —— #735가 구현되면 비용 투명화 폐루프가 완성됩니다.

**더 완전한 커뮤니티 실측 도구: dsh-usage**(작성자 kestiany, [#1169](https://github.com/deepseek-ai/deepseek-harness/discussions/1169) 수록 허가 받음). npm에 `0.1.0`이 이미 게시되어 있습니다(`dsh plugin --profile web add dsh-usage`로 설치 가능), Harness가 영속화한 세션 로그를 기반으로 계산하며 별도의 통계 데이터베이스가 필요 없습니다. 핵심 능력:
- **매 대화 라운드 끝 위치에 고정 표시**: `Total · Input · Cache · Output · Cost` —— #735가 빠뜨린 "매 라운드 토큰 수"를 정확히 채워주며, 입력/캐시 적중/출력을 구분해줍니다
- **Settings → Usage 완전한 사용량 페이지**: 총 토큰, 입력, 캐시 적중, 출력, 호출 횟수 및 **예상 비용**(Provider/모델에 가격 설정이 필요; usage/가격이 없으면 비용은 `--`로 표시되고, 대화 하단의 Cost는 생략됨, 불완전한 비용을 총 비용으로 오인하는 것을 방지)
- **52주 사용량 히트맵**(GitHub Contributions 스타일) + 모델/세션/단일 라운드별 조회
- DeepSeek Harness의 다른 모델과 Provider도 지원; `Cost`는 추정치이며 공급자의 최종 청구서를 대표하지 않음

**설치 없이: `session.jsonl.zstd`를 직접 읽기(#45 작성자 방안)** —— 어떤 플러그인도 설치할 필요 없이, dsh가 스스로 쓰는 세션 원본 데이터에 이미 모든 정보가 있습니다:
- `assistant/chunk`에서 `chunk.type`이 `usage`인 이벤트에는, 공급자가 반환한 `inputTokens` / `cacheReadTokens` / `outputTokens` / `reasoningTokens`가 담겨 있습니다 —— **요청별**입니다(모델 요청마다 하나씩), 세션 합계가 아닙니다
- `request/header` 이벤트에는 실제로 전송된 완전한 도구 스키마 배열과 시스템 프롬프트가 담겨 있습니다 —— 여러분 자신의 접두사 크기를 재는 데 추가 API 호출이 필요 없습니다

> **트러블(#45 작성자 실측)**: `zstdDecompressSync`는 첫 번째 frame을 읽으면 멈추는데, dsh는 **쓸 때마다 frame을 추가**합니다 —— 136줄짜리 세션을 그냥 압축 해제하면 1줄만 얻게 됩니다. frame magic(`28 B5 2F FD`)으로 나눈 후 하나씩 압축 해제해야 합니다.

**명령어 한 줄(#45 작성자 제공, 설치 없음)**: `npx dsh-lean audit` —— 요청별 적중 분해(적중/미적중/출력) + 여러분의 접두사에서 가장 큰 도구 스키마 몇 개를 출력합니다(데이터 출처는 위와 동일, 14.4 접두사 슬리밍 실측 참고).

**기억/압축 생태계 도구**(#1052 긴 세션 비용 절감 특집 댓글, 2026-08-14) —— "긴 세션 토큰 폭증"(원문 실측 7천만→1억)에 대해, 커뮤니티가 상호 보완적인 두 방안을 제시했습니다:

| 도구 | 작성자 | 포지셔닝 | 메커니즘 |
|---|---|---|---|
| **dsh-sgme**([freehul/sgme](https://github.com/freehul/sgme), npm 패키지 `dsh-sgme`) | freehul | 기억 엔진(근본 치료) | "대화 이력"과 "장기 기억"을 계층화: 매 라운드 무비용으로 디스크에 기록(L0, LLM을 거치지 않음) → 세션 종료 시 추출·중복 제거·병합(L1/L1.5/L2, 추출 전에 먼저 **가지치기**로 쓸모없는 도구 호출/중간 산출물을 제거, 실측 세션 내용 **65~96%** 절감) → 새 세션은 시나리오별로 관련된 기억 블록만 주입(순수 구조화 쿼리, 토큰을 태우지 않음) → 세부사항이 필요할 때 `memory_search`로 필요에 따라 검색 |
| **pi-quiet-tools**([pi2dsh](https://github.com/weijiafu14/pi2dsh)를 통해 장착) | weijiafu14 제공(freehul도 추천) | 도구 출력 압축(대증 치료) | **모델 컨텍스트에 들어가기 전에** 큰 도구 결과를 압축: 기본적으로 12,000자 또는 240줄을 초과하면 결정론적인 앞뒤 미리보기만 모델에 전달하고, 완전한 결과는 로컬 artifact에 저장했다가 필요할 때 모델이 다시 읽음; 임계값은 `QUIET_TOOLS_MAX_CHARS` / `QUIET_TOOLS_MAX_LINES`로 조절 가능. MCP/Playwright의 큰 반환값에 효과적(작성자 실측 40,799자를 압축해 폐루프 완성). 캐시와 호환됨: 14.1의 엄격한 접두사 캐시 규칙 참고 —— 캐시를 우회하지 않고, 오히려 "필연적으로 처음 miss하는" 도구 결과를 줄여줍니다 |

설치 예시(pi-quiet-tools, #1052 작성자 실측에서 발췌):

```sh
npm i -g pi2dsh
pi2dsh host --packages pi-quiet-tools@0.2.0 --out ./dsh-pi-quiet
dsh plugin --profile web add file:$PWD/dsh-pi-quiet
```

> 둘은 충돌하지 않습니다: pi-quiet-tools는 "큰 도구 결과가 반복적으로 컨텍스트에 들어가는" 문제를 해결하고, dsh-sgme는 "긴 세션이 쓸수록 비싸지는/연속성" 문제를 해결합니다 —— 전자는 즉시 효과가 있고, 후자는 세션 간 기억 이전이 필요한 시나리오에 적합합니다(#1052 댓글의 합의: "대화 이력"과 "장기 기억"을 분리해, 이력은 굴러가게 두고 기억은 필요에 따라 주입).

## 14.8 비용 관련 트러블슈팅 목록

| # | 트러블 | 증상 | 해법 |
|---|---|---|---|
| 1 | 캐시 적중을 "모델이 빨라졌다"고 오판 | A/B 비교가 1초 vs 110초에 오도됨(제6장 트러블 #6) | 비교 테스트는 **완전히 새로운 prompt**를 사용 |
| 2 | 잦은 새 세션 생성이 비용을 낭비함 | 매 작업이 콜드 스타트로, 입력이 전체 가격 | 긴 작업/배치는 세션 연속성 유지 |
| 3 | 설정 변경이 조용히 적중률을 죽임 | 적중 %가 갑자기 떨어지고 비용이 오름 | 통계 행의 적중 %를 모니터링, 접두사를 안정적으로 유지 |
| 4 | 총 토큰만 보고 비용을 오판 | 1만 토큰에서 90% vs 10%가 7.0배 차이 | 적중/미적중을 나눠서 확인(#735 제안) |
| 5 | 예산에서 출력 쪽을 빠뜨림 | 입력 가격으로만 계산해 금액이 안 맞음 | 공식 가격 페이지/14.1 가격표로 출력 가격을 보충(출력 = 미적중의 3배, 캐시 할인 없음) |
| 6 | 강도를 무분별하게 사용 | 배치 작업에 `max`를 써서 비용이 두 배가 됨 | 배치는 `low`, 복잡한 작업만 `max` |
| 7 | 피크/오프피크 경계를 넘나들며 금액 비교 | 비용 대조 실험 결론이 틀림(#45 작성자 실측 경험) | 토큰만 비교하고 금액은 비교하지 말 것(경계를 넘으면 접두사 단가가 다름, 14.2 기준 주의사항 2 참고) |

## 14.9 의사결정 제안 빠른 참조

| 시나리오 | 제안 |
|---|---|
| 긴 도구 체인 작업(20-50단계) | `high` + 세션 연속성 + 접두사 안정; 240만 입력 규모 ≈ $0.032(97% 적중, 오프피크) |
| 배치/단순 라운드 | `low` + 같은 세션에서 배치(적중 보너스가 가장 큼) |
| 복잡한 추론/디버그 | `max`(비용으로 품질을 사는 것), 단발성 작업은 콜드 스타트를 감수할 만함 |
| 비용에 민감한 배치 처리 | `low` + headless + 단일 세션 순차 처리 |
| 긴 작업(배치 리팩터링/테스트/agent 긴 작업) | **오프피크**로 옮기기(한국시간 저녁 8시 이후/아침 8시 이전), 청구서가 바로 절반(적중률과 곱셈으로 누적, 14.1) |
| 성능/비용 비교 테스트 | 완전히 새로운 prompt + 고정된 강도 + 여러 번 실행해 중앙값 취하기; 피크/오프피크 경계를 넘는 그룹은 토큰만 비교하고 금액은 비교하지 말 것(제6장 6.4/6.6, 14.2 기준 주의사항 2) |
| 적중률이 비정상적으로 하락 | 먼저 접두사가 바뀌었는지 확인(설정/스킬 카탈로그/모델 강도) |

## 자주 묻는 질문 FAQ

**Q1: 캐시 적중률은 최대 얼마까지 올라가나요?**
핸드북 실측 97%(제5장 5.1.1); 커뮤니티 긴 실행 실측은 99.7%까지 달성했습니다([#560](https://github.com/deepseek-ai/deepseek-harness/discussions/560)). 하지만 **완전히 새로운 작업/콜드 스타트에서는 눈에 띄게 낮아집니다**(제12장 12.5) —— 적중률은 "방법"의 함수이지, 모델의 상수가 아닙니다.

**Q2: `low` 강도는 품질을 크게 떨어뜨리나요?**
단순 결정론적 작업(파일 조작, 배치 처리)은 거의 차이가 없습니다; 복잡한 추론, 긴 체인 계획, 디버그에 `low`를 쓰면 핵심 단계를 놓칠 수 있습니다(제6장 FAQ Q3). 일상에는 `high`, 배치/단순 작업은 `low`로 전환하는 것을 권장합니다.

**Q3: 공식은 언제 매 라운드 토큰 표시를 제공하나요?**
[#735](https://github.com/deepseek-ai/deepseek-harness/discussions/735)는 2026-08-14에 제기된 요구사항 게시물입니다(매 라운드 토큰 + provider/model 식별자, 14.7 참고), **아직 구현되지 않았습니다**. 과도기에는: 세션 통계 행의 적중 % + 커뮤니티 `dsh-plugin-cost-tracker`(제9장)나 `dsh-usage`(14.7)를 사용하세요.

**Q4: 서드파티 게이트웨이/자체 구축 provider도 캐시 할인을 받나요?**
캐시 할인은 DeepSeek API 측의 능력입니다(제5장 가격표); 서드파티 게이트웨이의 캐시 지원과 과금 방식은 해당 가격 페이지를 확인해야 합니다(추론, 미실측).

**Q5: 왜 캐시가 적중되면 작업이 눈에 띄게 빨라지나요?**
적중된 접두사 부분은 다시 계산할 필요가 없어, 첫 토큰 시간이 자릿수 단위로 단축됩니다(콜드 스타트 ~110초 vs 핫 캐시 ~1초, 제1장 실측). 판단 방법: 첫 토큰이 갑자기 10초+에서 1초 미만으로 떨어지면 적중했을 가능성이 큽니다(제6장 FAQ Q4). 성능 비교를 할 때는 완전히 새로운 prompt를 써서 캐시 간섭을 피하세요(제6장 트러블 #6).

**Q6: 언제 실행하는 것이 가장 저렴한가요?**
2026-08-16부터 피크/오프피크 요금제 시행(14.1): 피크 시간 UTC 01:00-04:00 + 06:00-10:00(한국시간 오전 10:00-13:00 + 오후 15:00-19:00), 오프피크 가격은 피크의 절반입니다. 국내(중국) 일상 코딩 시간은 거의 전부 피크 구간입니다; 긴 작업(배치 리팩터링/테스트/agent 긴 작업)을 저녁이나 아침 8시 이전으로 옮기면 청구서가 바로 절반이 됩니다 —— 적중률과 곱셈으로 누적되며, 설정을 바꿀 필요가 없습니다.
