# 제 9 장: MCP, 서브에이전트, 워크플로우

> 본 장의 목표: dsh의 세 가지 확장 능력을 이해합니다 —— MCP(외부 도구 연동), 서브에이전트(병렬 작업), 워크플로우(다단계 오케스트레이션). **이것들은 dsh를 "단일 Agent"에서 "Agent 시스템"으로 업그레이드하는 스위치입니다.**

> ⚠️ 본 장은 공식 아키텍처 문서(`packages/AGENTS.md`)와 패키지 구조를 정리한 것입니다; 일부 기능 예시는 「미실측」으로 표시되어 있습니다 —— rc 버전은 반복 속도가 빠르므로, 구체적인 사용법은 공식 changelog를 기준으로 삼으세요.

## TL;DR(본 장 핵심, 30초 버전)

1. **MCP = Agent에 외부 도구를 꽂는 것**: MCP 프로토콜로 데이터베이스, 브라우저, 회사 내부 시스템 등을 연동 —— 내장 도구를 먼저 익히고, 명확한 공백이 있을 때 MCP를 추가하세요
2. **서브에이전트 = 병렬로 일하기**: 작업을 하위 Agent에 위임해 병렬로 실행(대규모 저장소 조사, 긴 작업 분해, 독립 검증) —— 단일 Agent를 먼저 잘 쓴 다음 서브에이전트를 도입하세요
3. **워크플로우 = 결정론적 프로세스 오케스트레이션**: "여러 라운드의 대화"와 달리, 워크플로우는 단계를 프로세스로 정의해 순서/조건에 따라 실행합니다 —— 데이터 가져오기→정제→리포트→검증에 적합
4. **조합하면 = Agent 시스템**: 부모 Agent가 계획 → 서브에이전트가 병렬 조사 → 도구 체인 + MCP → 워크플로우로 취합 → 산출물
5. **초보자 4단계 경로**: 단일 Agent + 내장 도구 → + MCP → + 서브에이전트 → + 워크플로우(단계적으로 쌓고, 건너뛰지 마세요)

## 9.1 MCP: 외부 도구 생태계 연동

**MCP(Model Context Protocol)**는 "Agent에 외부 도구를 꽂는" 개방형 프로토콜입니다. dsh는 `mcp` 클라이언트 패키지(`@deepseek-ai/dsh-mcp-client`)를 제공합니다.

**할 수 있는 것**: MCP를 통해 어떤 MCP 서버든(데이터베이스, 브라우저, 차트, 회사 내부 시스템……) 연동할 수 있습니다 —— 예를 들어 커뮤니티에 이미 등장한 `dsh-plugin-cost-tracker`(토큰 추적)가 MCP/플러그인 형태입니다.

**초보자 포지셔닝**: MCP는 "생태계 확장"이니, dsh에서 명확한 도구 공백이 생긴 후에 연동하세요. 내장 도구를 먼저 익히고, 그다음 MCP를 추가하세요.

## 9.2 서브에이전트(subagent): 병렬로 일하기

**무엇인가**: 작업을 하위 Agent에 위임해 병렬로 실행합니다(`packages/subagent/*`).

**전형적인 시나리오**:
- 대규모 저장소의 여러 모듈 조사(모듈마다 서브에이전트 하나씩)
- 긴 작업 분해(부모 에이전트가 계획, 서브에이전트가 실행)
- 독립 검증(서브에이전트가 교차 확인)

**초보자에게**: 서브에이전트는 "고급 무기"입니다 —— 단일 Agent를 먼저 잘 쓰고, 작업 분해를 이해한 후에 서브에이전트를 도입하세요. 잘못된 예시는 "무슨 작업이든 서브에이전트를 여는 것"으로, 오히려 조율 비용만 늘어납니다.

**알려진 제약(커뮤니티 피드백)**: 현재 **서브에이전트 모델을 동적으로 지정할 수 없습니다** —— 서브에이전트 모델은 부모 Agent 설정을 따라가며, 커뮤니티는 이미 디스커션에서 피드백했습니다([#118](https://github.com/deepseek-ai/deepseek-harness/discussions/118) 댓글, Claude Code의 "서브에이전트 모델을 지정할 수 있는" 경험과 대조). 서로 다른 모델 능력이 필요할 때는, 현재로서는 부모 Agent의 모델 설정을 전체적으로 전환하거나, 독립된 세션으로 나누어 각각 지정하는 수밖에 없습니다.

## 9.3 워크플로우(workflow): 다단계 오케스트레이션

**무엇인가**: `packages/workflow/*`가 다단계 워크플로우 오케스트레이션을 제공합니다(worker-thread provider + tool Consumer).

**"여러 라운드의 대화"와의 차이**: 일반 대화는 "모델이 자유롭게 진행"하는 것이고, 워크플로우는 "단계를 프로세스로 정의해 순서/조건에 따라 실행"하는 것입니다 —— **결정론적 프로세스**에 적합합니다(예: 데이터 가져오기 → 정제 → 리포트 생성 → 검증).

**공식 예시**(`packages/examples/`): 실행 가능한 cordis.yml 워크플로우 예시가 있습니다.

## 9.4 조합하기: "Agent 시스템"은 어떻게 생겼는가

```text
당신의 프롬프트(목표)
  ↓
부모 Agent(계획)
  ├── 서브에이전트 A: 모듈 A 조사(병렬)
  ├── 서브에이전트 B: 모듈 B 조사(병렬)
  └── 도구 체인: read/grep/bash + MCP(데이터베이스)
  ↓
워크플로우(예: 검증 → 취합 → 리포트 출력)
  ↓
산출물(열람/추적 가능)
```

**초보자 경로 제안**:
1. **1단계**: 단일 Agent + 내장 도구(제2-5장)
2. **2단계**: + MCP(외부 도구 연동)
3. **3단계**: + 서브에이전트(병렬)
4. **4단계**: + 워크플로우(결정론적 프로세스)

## 9.5 커뮤니티 생태계 예시(2026-08-13 스냅샷)

공식 Discussion에 이미 등장한 커뮤니티 프로젝트:
- `dsh-plugin-cost-tracker` —— 토큰 비용을 실시간 추적(플러그인/MCP 형태)
- 플러그인 개발/속도 개선류(본 백서 제4장의 예제 속도 개선 플러그인 등)

생태계는 빠르게 성장하고 있습니다 —— **지금이 진입해서 블록을 쌓기 좋은 때입니다**.

## 9.6 MCP 연동 설정 예시

아래는 `cordis.patch.yml`에서 MCP 클라이언트를 장착하는 **설정 조각**입니다(문법은 제3장 3.2절과 동일, 커뮤니티 토큰 추적 플러그인을 예로 듦):

```yaml
- insert:
    - id: mcp-client
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        servers:
          - name: cost-tracker
            command: npx
            args: ['-y', 'dsh-plugin-cost-tracker']
            env:
              DSH_API_KEY: '${DSH_API_KEY}'
```

**필드 설명**: `id`(cordis 체인 식별자), `name`(npm 패키지 이름), `config.servers`(서버 목록, 서버마다 독립된 프로세스), `command`/`args`(시작 명령과 인자), `env`(환경 변수, `${VAR}`로 호스트 변수 참조 가능).

> ⚠️ 위 설정은 `packages/mcp/` 디렉터리 구조와 cordis 장착 문법을 기반으로 추론한 것이며, 구체적인 필드는 공식 문서를 기준으로 삼으세요(rc 단계에서 변경될 수 있음). 검증 방법(추론, 미실측): 장착 후 `dsh web`을 재시작하고, 토큰 카운팅과 관련된 작업을 보내 로그에 MCP 호출 기록이 나타나는지 관찰하세요.

## 9.7 서브에이전트 설정 예시

병렬 서브에이전트는 `packages/subagent/*`를 통해 제공됩니다. 아래는 `cordis.patch.yml`에서 **서브에이전트 능력을 활성화**하는 설정 조각입니다:

```yaml
- insert:
    - id: subagent
      name: '@deepseek-ai/dsh-subagent'
      config:
        maxConcurrency: 3
        timeout: 120000
```

**적용 시나리오와 동시성 전략**:

| 시나리오 | 서브에이전트 수 | 부모 에이전트의 역할 | 서브에이전트의 역할 |
|---|---|---|---|
| 대규모 저장소 여러 모듈 조사 | 3-5개 | 모듈 경계 구분, 결론 취합 | 각 모듈을 독립적으로 조사 |
| 긴 작업 분해 | 2-3개 | 하위 작업 분할, 완전성 검증 | 각 하위 작업을 독립 실행 |
| 독립 검증 | 1-2개 | 결론과 검증 기준 제공 | 교차 확인 |
| 여러 파일 병렬 편집 | 2-4개 | 파일 범위 고정, 충돌 방지 | 서브에이전트마다 다른 파일에 쓰기 |

> ⚠️ `maxConcurrency`와 `timeout`은 패키지 이름과 cordis 관례를 기반으로 추론한 것입니다(추론, 미실측). 컨텍스트 격리 메커니즘은 공식 `packages/subagent/README.md`를 참고해야 합니다.

## 9.8 워크플로우 YAML 예시

아래는 **결정론적 워크플로우**의 `cordis.patch.yml` 조각으로, "데이터 가져오기 → 정제 → 리포트 → 검증"의 4단계를 시뮬레이션합니다(제10장 사례 A의 작업 구조 참고):

```yaml
- insert:
    - id: workflow
      name: '@deepseek-ai/dsh-workflow'
      config:
        steps:
          - id: fetch
            tool: bash
            command: 'curl -o raw.json https://api.example.com/data'
          - id: clean
            tool: bash
            command: 'python clean.py raw.json cleaned.json'
            dependsOn: [fetch]
          - id: report
            tool: bash
            command: 'python visualize.py cleaned.json chart.png'
            dependsOn: [clean]
          - id: validate
            tool: bash
            command: 'python verify.py cleaned.json'
            dependsOn: [report]
```

**사례 A와의 대응**: 워크플로우는 `dependsOn`으로 순서를 명시적으로 정의하는 반면, 사례 A의 "여러 라운드 대화"는 모델이 자유롭게 도구를 결정합니다. 워크플로우는 "단계가 고정된" 경우에 적합하고, 자유로운 대화는 "탐색적인" 경우에 적합합니다.

> ⚠️ `steps`/`dependsOn`은 `packages/workflow/` 패키지 이름과 일반적인 DSL을 기반으로 추론한 것입니다(추론, 미실측). 공식 `packages/examples/`에 실행 가능한 예시가 있으니 이를 기준으로 삼는 것을 권장합니다.

## 9.9 세 가지 비교표

| 항목 | MCP | 서브에이전트 | 워크플로우 |
|---|---|---|---|
| **적용 시나리오** | 외부 시스템 연동(데이터베이스/브라우저/내부 API) | 큰 작업의 병렬 분해(조사/검증/여러 모듈) | 결정론적 파이프라인(가져오기→정제→리포트→검증) |
| **복잡도** | 중간(서버 설정 + 프로토콜 이해 필요) | 높음(작업 분해 설계 + 결과 취합 필요) | 낮음-중간(YAML 설정, 의존성 그래프 디버깅은 다소 번거로움) |
| **실패 처리** | 서버 다운 → 재연결이나 오류 반환(추론, 미실측) | 서브에이전트 하나 실패 → 부모 에이전트가 재시도/무시/종료 결정 | 단계 하나 실패 → 선택적 일시정지/건너뛰기/롤백(추론, 미실측) |
| **성능 오버헤드** | 추가 프로세스 통신 오버헤드(stdio/sse) | 병렬로 벽시계 시간 절약, 대신 조율 오버헤드 증가 | 순차 실행, 추가 모델 오버헤드 없지만 병렬화 이득도 없음 |

**결정 가이드**: 명확한 도구 공백이 있다면 → MCP; 작업이 서로 의존하지 않는 여러 조각으로 나눌 수 있다면 → 서브에이전트; 단계가 고정되어 있고 엄격한 순서가 필요하다면 → 워크플로우. 세 가지는 조합할 수 있습니다: 서브에이전트가 병렬로 조사 → 내부에서 MCP로 데이터베이스 조회 → 워크플로우로 리포트를 취합.

## 9.10 트러블슈팅 보충

| # | 트러블 | 증상 | 해법 |
|---|---|---|---|
| 1 | MCP 연결 실패 | 장착 후 시작 오류나 MCP 도구 무응답 | `command`/`args` 확인; 먼저 수동으로 `npx -y xxx`를 실행해 검증(추론, 미실측) |
| 2 | 서브에이전트 컨텍스트 격리 | 서브에이전트가 부모 Agent의 이력을 보지 못해 중복 질문 발생 | 부모 에이전트가 위임할 때 핵심 컨텍스트를 작업 설명에 적어둠(추론, 미실측) |
| 3 | 워크플로우 단일 단계 실패 | 특정 단계의 `bash`가 0이 아닌 값을 반환해도 후속 단계가 계속 실행됨 | `onError: pause`를 설정하거나 각 단계 후 검증 스크립트를 추가(추론, 미실측) |
| 4 | 서브에이전트 파일 충돌 | 여러 서브에이전트가 동시에 같은 파일에 씀 | 부모 에이전트가 계획할 때 파일 경계를 구분(추론, 미실측) |
| 5 | MCP 환경 변수 미주입 | `${DSH_API_KEY}`가 빈 값으로 해석됨 | 호스트 shell에서 이미 `export`했는지 확인; 또는 하드코딩(로컬 테스트에만)(추론, 미실측) |

> "추론, 미실측"으로 표시된 모든 내용은 `packages/` 디렉터리 구조와 cordis 설정 관례를 기반으로 추론한 것이며, 본 백서의 실기 검증 결과가 아닙니다. rc 단계에서는 공식 문서를 기준으로 삼으세요.

## 9.11 4단계 초보자 경로(검수 기준 포함)

9.4절의 "4단계"를 **각 단계마다 명확한 검수 기준이 있는** 업그레이드 경로로 확장합니다:

| 단계 | 능력 | 검수 기준(다음 단계로 넘어가도 되는지 아는 법) | 참고 절 |
|---|---|---|---|
| **1단계** | 단일 Agent + 내장 도구 | 독립적으로 완료 가능: 파일 생성 → 검색 → 편집 → 실행 검증, 전 과정에서 막히지 않음 | 제2-5장 |
| **2단계** | + MCP | MCP 서버 하나를 성공적으로 장착하고, 작업 중 그 도구를 호출하며 로그가 호출을 증명함 | 9.1절 + 9.6절 |
| **3단계** | + 서브에이전트 | 병렬 서브에이전트 작업을 한 번 성공적으로 시작(예: 모듈 2개를 동시 조사), 부모 에이전트가 결과를 취합할 수 있음 | 9.2절 + 9.7절 |
| **4단계** | + 워크플로우 | 3단계 이상의 워크플로우를 성공적으로 설정하고 실행, 각 단계가 `dependsOn` 순서대로 실행됨 | 9.3절 + 9.8절 |

**왜 건너뛰면 안 되는가**: 1단계가 통과되지 않은 상태 → 2단계에서 오류가 나도 설정이 잘못된 건지 기본 도구 체인을 못 쓰는 건지 판단할 수 없음; 2단계가 통과되지 않은 상태 → 3단계에서 병렬화가 문제를 증폭시킴; 3단계가 통과되지 않은 상태 → 4단계 YAML을 작성해도 틀림. 1단계에서 2단계로 넘어가기 전에, 먼저 제8장 8.1절 능력 패키지 지도를 읽으세요 —— 필요한 것이 이미 내장되어 있는지 확인해, "이미 있는 능력"에 MCP를 설정하는 낭비를 피하세요.

## 자주 묻는 질문 FAQ

**Q1: MCP는 무엇인가요? dsh 플러그인과는 무엇이 다른가요?**
MCP는 "Agent에 외부 도구를 꽂는" 개방형 프로토콜입니다. 플러그인은 dsh 런타임 안에서 능력을 등록합니다(host 반쪽이 Node 프로세스에서 실행됨); MCP 서버는 독립된 프로세스로, 프로토콜을 통해 통신합니다. 플러그인은 깊게 통합되고 성능이 좋으며; MCP는 결합도가 낮고 재사용 가능해 기존 시스템을 연동하기에 적합합니다.

**Q2: 서브에이전트는 어떻게 "병렬"로 동작하나요? 충돌은 없나요?**
서브에이전트는 부모 Agent가 위임하며, 각자 독립적으로 실행됩니다(`packages/subagent/*`). 병렬 실행 시 각 서브에이전트는 자신의 컨텍스트를 가지며 서로 간섭하지 않습니다. 하지만 여러 서브에이전트가 같은 파일을 수정하면 충돌할 수 있으니 —— 작업을 분해할 때 겹치지 않도록 하는 것을 권장합니다.

**Q3: 워크플로우의 "결정론적 프로세스"는 무슨 뜻인가요? 모델이 자유롭게 진행하는 것과 무엇이 다른가요?**
워크플로우는 단계를 프로세스로 정의하고(예: cordis.yml), 순서/조건에 따라 실행하며, 매 단계에서 무엇을 할지가 지정되어 있습니다. 여러 라운드 대화는 "모델이 자유롭게 진행"하는 것입니다. 결정론적 프로세스는 "반드시 고정된 단계로 진행해야 하는" 시나리오에 적합하고, 자유로운 진행은 "탐색적인 작업"에 적합합니다.

**Q4: MCP 서버(예: 데이터베이스)를 하나 연결하고 싶은데, 구체적으로 어떻게 하나요?**
(공식 changelog를 기준으로) ① `@deepseek-ai/dsh-mcp-client` 설치; ② `cordis.patch.yml`에 장착(9.6절 참고); ③ 서버 주소/명령 설정; ④ `dsh web` 재시작. 자세한 내용은 공식 `packages/mcp/` 문서 참고.

**Q5: 서브에이전트와 "dsh 프로세스를 여러 개 여는 것"은 무엇이 다른가요?**
서브에이전트는 dsh 내부의 위임 메커니즘으로(`packages/subagent/*`), 부모 Agent의 컨텍스트와 세션을 공유합니다. 다중 프로세스는 완전히 독립된 세션입니다. 서브에이전트는 "작업을 분해한 후 병렬 실행 + 결과 취합"에 적합하고, 다중 프로세스는 "완전히 독립적인 작업"에 적합합니다.

**Q6: 본 장에서 일부 기능이 "미실측"이라고 했는데, 어떤 기능이 이미 사용 가능한지 어떻게 아나요?**
공식 `packages/AGENTS.md`와 `packages/` 디렉터리를 확인하세요. 완전한 소스 코드 + 예시가 있는 기능은 기본적으로 사용 가능합니다; 패키지 이름만 있고 문서가 없는 것은 아직 개발 중일 수 있습니다. rc 단계에서는 공식 changelog를 기준으로 삼으세요.
