## 사례 C: HTML 페이지 구축과 파싱(Web 프론트엔드 영역)

### 작업 설명

표+폼+차트가 포함된 합성 HTML 페이지(`page.html`, 8행의 제품 재고 데이터)를 기반으로, dsh에게 서드파티 의존성 없이 지정된 표를 추출해 CSV 형식으로 stdout에 출력하는 Python 파싱 스크립트를 작성하게 하고, 마지막에 실행 검증하도록 요구했습니다.

### 입력 산출물

- `page.html`: 합성 전자제품 재고 대시보드, `<table id="product-table">`(8행 데이터 × 7열), 재입고 폼, CSS 차트 포함

### dsh 실행 과정

- **시작**: 2026-08-13T12:17:54-04:00
- **종료**: 2026-08-13T12:21:12-04:00
- **소요 시간**: 약 3분 18초

### 도구 체인 경로(출력에서 추론)

1. `page.html` 읽기(파일 시스템 도구)
2. HTML 구조 분석(의미 이해)
3. `parser.py` 작성(코드 생성 도구)
4. `python parser.py` 실행(shell 실행 도구)
5. 출력과 원본 표 대조(검증 도구)

### 산출물 목록

| 파일 | 설명 |
| --- | --- |
| `case3/page.html` | 입력 HTML(합성 데이터) |
| `case3/parser.py` | dsh가 생성한 파싱 스크립트(표준 라이브러리 `html.parser`, 78줄) |
| `case3/case3-output.txt` | 실행 기록과 검증 결과 |

### 검증 결과

- **파일 존재**: parser.py ✓, case3-output.txt ✓
- **내용 확인**: parser.py는 `HTMLParser` 서브클래스를 사용, 표 깊이 카운팅, 안전 종료 메커니즘 포함
- **실행 검증**: 9행 × 7열 CSV 출력, page.html의 표와 필드별로 대조해 일치
- **인코딩**: UTF-8, BOM 없음, 서드파티 의존성 없음

### 출력 하이라이트

- **의존성 없음 전략**: dsh가 BeautifulSoup 대신 표준 라이브러리 `html.parser`를 능동적으로 선택, "최소 의존성"에 대한 트레이드오프를 보여줌
- **견고성 설계**: `table_depth` 중첩 카운팅을 구현해, 페이지 안에 중첩된 표가 있어도 파싱 범위를 벗어나지 않도록 방지
- **경로 독립성**: `os.path.dirname(os.path.abspath(__file__))`로 HTML 파일을 위치 확인, 실행 디렉터리에 의존하지 않음

## 사례 D: 코드 리팩터링(소프트웨어 엔지니어링 영역)

### 작업 설명

약 200줄의 절차형 Python 주문 처리 스크립트(중복 코드 `calc_order_total` / `calc_order_total_v2` 포함)를 주고, dsh에게 객체지향 + 책임 분리 스타일로 리팩터링하되 동작은 그대로 유지하고 테스트로 검증하도록 요구했습니다.

### 입력 산출물

- `legacy_orders.py`: 절차형 스타일, 전역 상태 + 함수 집합, 중복된 금액 계산 로직 포함

### dsh 실행 과정

- **시작**: 2026-08-13T12:22:00-04:00
- **종료**: 2026-08-13T12:26:37-04:00(테스트 추가 시간)
- **소요 시간**: 약 4분 37초

### 도구 체인 경로(출력에서 추론)

1. `legacy_orders.py` 읽기와 분석(코드 분석 도구)
2. 중복 코드와 책임 경계 식별(의미 이해)
3. `orders_refactored.py` 작성(코드 생성 도구)
4. `test_refactor.py` 작성(테스트 생성 도구)
5. 테스트 실행과 출력 비교(shell 실행 + 검증 도구)

### 산출물 목록

| 파일 | 설명 |
| --- | --- |
| `case4/legacy_orders.py` | 입력 코드(절차형, 약 200줄) |
| `case4/orders_refactored.py` | 리팩터링된 코드(OOP, 312줄, dataclass + 책임 분리) |
| `case4/test_refactor.py` | 동작 일치성 테스트 스크립트(186줄, 17개 항목 검사) |
| `case4/case4-output.txt` | 실행 기록과 테스트 결과 |

### 검증 결과

- **파일 존재**: orders_refactored.py ✓, test_refactor.py ✓, case4-output.txt ✓
- **테스트 커버리지**: 17/17 항목 전부 PASS, 종료 코드 0
  - format_report() 출력이 완전히 일치(고정 타임스탬프 이후)
  - export_json() 텍스트 + 파싱 후 데이터 일치
  - 모든 조회 함수(get_customer_orders ×4, get_product_sales ×5, get_region_summary, get_pending_orders) 일치
  - calc_order_total(알 수 없는 ID)이 모두 0.0을 반환
  - 스크립트 전체 실행 산출물(report.txt, orders.json) 일치
- **결론**: 리팩터링 전후 동작이 완전히 일치

### 출력 하이라이트

- **정확한 중복 식별**: dsh가 `calc_order_total`과 `calc_order_total_v2`가 같은 로직의 두 구현임을 정확히 식별해, `Order.total()` 단일 진입점으로 병합
- **책임 분리 설계**: Product/Customer/Order(도메인 모델) + OrderProcessor(데이터 저장소와 조회) + ReportGenerator(리포트와 내보내기), SOLID 원칙에 부합
- **하위 호환성**: 모듈 레벨 함수 인터페이스(`load_data()`, `calc_order_total()` 등)를 유지해 바로 교체 호출 가능
- **테스트 깊이**: 함수 반환값만 비교하는 게 아니라 스크립트 레벨 전체 실행 산출물(report.txt / orders.json)도 비교했고, 타임스탬프 차이도 처리함
- **샌드박스 인식**: dsh가 `tempfile.mkdtemp`의 0700 ACL이 샌드박스에서 쓸 수 없음을 알아채고 능동적으로 `os.makedirs` 방식으로 변경
