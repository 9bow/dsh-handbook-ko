# 부록 C: 동일 모델 × 다른 Agent 실측 비교(Benchmark)

> 실측일: 2026-08-13 ｜ 모델: deepseek-v4-flash(같은 opencode-go 게이트웨이, 같은 API key) ｜ Agent: dsh / opencode / omp
> 목적: **모델 변수를 통제하고, Agent 엔지니어링 레이어의 차이를 비교**(프롬프트, 도구 체인, 라운드 관리).
> 확장: 2026-08-13에 T4(markdown 리포트 생성) / T5(다중 파일 소규모 리팩터링) 추가, 샘플 3회 → 5개 작업 × 3회.

## 해석

1. **정확도는 세 곳 모두 동일(45/45)** —— 5개 작업 × 3회 모두 정확. 같은 모델 기준으로, Agent 엔지니어링 레이어의 차이는 주로 **능력의 상한**이 아니라 **효율**에서 나타납니다; 문서 생성과 다중 파일 리팩터링이라는 두 가지 새 작업 유형을 추가해도 정확도 차이는 나타나지 않았습니다.
2. **총 소요 시간 순서는 안정적**: omp < dsh < opencode(3회 모두 일치, 중앙값 합계 70초 / 130초 / 172초).
3. **작업 유형이 효율 차이에 미치는 영향**(이번 확장의 핵심 발견) —— 소요 시간 패턴으로 5개 작업을 세 부류로 나눌 수 있습니다:
   - **단일 단계 경량**(T1 파일 생성 / T2 검색 통계): agent 간 격차가 **가장 큼**. opencode 35/37초 vs omp 10/11초(약 **3.4배**). 작업이 단순할수록 순수한 "시작 + 도구 호출 한 번"의 오버헤드에 가까워져, opencode의 시작/프레임워크 오버헤드 비중이 더 커집니다.
   - **다단계 실행 + 검증**(T3 버그 수정 + 검증 실행 / T5 다중 파일 리팩터링 + 테스트): dsh와 opencode의 격차가 이 유형에서 **뚜렷이 좁혀집니다**(T5: 19초 vs 28초; T3: 48초 vs 42초로 오히려 역전). 다중 도구 체인 시나리오에서는 양쪽 모두 파일을 여러 번 읽고/수정하고/명령을 실행해야 하므로, 프레임워크 레이어의 "매 단계 사고" 비용이 시작 오버헤드 차이를 상쇄합니다; dsh의 우위는 T5에서 가장 뚜렷하고(19초, omp의 13초에 근접), T3의 버그 위치 확인은 여전히 dsh를 다소 느리게 만듭니다.
   - **문서 생성**(T4 데이터 읽기 → 리포트 작성 → 자체 검토): agent 간 격차가 **가장 작음**(omp 21초 / dsh 26초 / opencode 30초, 약 1.4배). 리포트 생성은 "한 번 읽고 + 한 번 긴 텍스트를 쓰는" 루프로, 소요 시간이 주로 모델의 **출력 토큰 수**에 좌우되며, Agent 엔지니어링 레이어가 최적화할 수 있는 도구 왕복이 적어 세 곳이 비슷해집니다.
4. **직관에 반하는 포인트: T5(리팩터링+테스트)가 T4(리포트 작성)보다 대체로 더 빠름**(dsh 19초<26초, omp 13초<21초; opencode만 28초≈30초). 이유: 리팩터링은 "짧은 텍스트 코드 편집 + 초 단위 `python main.py` 검증"의 루프로 매 단계 모델 사고가 짧지만; markdown 리포트 작성은 한 번의 비교적 긴 텍스트 생성이 필요해 출력 시간 비중이 높습니다 —— 제6장의 "도구 체인 작업 시간의 90%가 모델 사고/생성에 쓰인다"는 성능 모델과 일치합니다.
5. **omp의 우위 폭은 작업 유형에 따라 달라집니다**: 검색 통계류가 가장 크고(T2는 opencode의 3.4배), 문서 생성류가 가장 작습니다(T4는 겨우 1.4배). 이는 omp의 강점이 주로 **라운드가 적고 도구 호출이 빠른 것**에 있지, 모델 자체에 있지 않음을 보여줍니다; 작업이 긴 텍스트 생성 위주가 되면, 어떤 agent의 엔지니어링 레이어도 모델 출력 시간을 더 압축하기 어렵습니다.
6. **변동성 안내**: opencode는 T4 2회차에서 49초의 이상치가 나타났고(나머지 두 번은 30초), dsh는 T3에서 변동이 가장 큽니다(27→74초). 여러 회차의 중앙값은 이런 네트워크/도구 체인 흔들림을 흡수할 수 있지만, 단일 회차 비교는 신중해야 합니다.
7. **dsh의 포지셔닝**: dsh는 중간이며, headless는 "런타임 + 플러그인 생태계"입니다 —— **같은 모델이라도, 플러그인(예: 속도 개선 플러그인으로 추론 강도 낮추기)을 통해 소요 시간을 더 최적화할 수 있습니다**(제6장 참고); T5 실측이 이미 omp에 근접해, 다중 파일 리팩터링류 작업이 dsh의 상대적 강점임을 보여줍니다.
8. **샘플 경고**: 3회 × 5개 작업, 같은 게이트웨이 같은 key, 네트워크 흔들림 포함 —— 방향은 신뢰할 수 있지만, 절대값은 환경에 따라 변동할 것입니다.

## 재현 가능

```bash
# 세 agent의 명령어(독립 디렉터리)
dsh --profile headless "작업"
opencode run "작업" --model opencode-go/deepseek-v4-flash
omp "작업" --model deepseek-v4-flash --print
```

T4/T5 작업 원문(T1-T3는 이전 버전 기록 참고):

```text
T4: 현재 디렉터리의 data.json 데이터를 읽고, markdown 리포트 report.md를 생성해: 각 행 데이터의 표(제품/판매량/단가 3열)와 요약(총 판매량, 총 매출, 최다 판매 제품)을 포함하고, 생성 후 요약 숫자가 data.json과 일치하는지 스스로 검토한 다음, 완료되면 "생성 완료"라고 답해
T5: mathops.py를 리팩터링해: multiply 함수 안의 곱셈 로직을 비공개 헬퍼 함수 _multiply(a, b)로 추출하고, multiply는 _multiply를 호출하도록 바꿔; main.py는 mathops.py에 의존하고 assert 테스트를 포함하니 main.py는 수정하지 마; 리팩터링 후 python main.py를 실행해 모든 assert가 통과하는지 검증하고, 완료되면 "리팩터링 완료"라고 답해
```

> 전체 작업 정의, 합성 데이터, 산출물: `~/agent-bench/bench-ext/`(T4/T5는 agent별 독립 디렉터리); T1-T3는 `~/agent-bench/` 참고. 백서 저장소 내 `benchmark/` 디렉터리는 계획 중입니다.
