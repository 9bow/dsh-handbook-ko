# 제 12 장: 알려진 한계와 경계 —— 솔직한 버전

> 본 장의 목표: 과대포장도 폄하도 하지 않고, dsh의 현재 **알려진 한계**와 **사용 경계**를 나열합니다. 본 백서를 쓰는 시점에 dsh는 여전히 `0.1.0-rc.6`(프리릴리스 단계)이며, 이 한계들은 "지금 이 순간의 사실"이지 "영원한 숙명"이 아닙니다 —— 버전이 반복되면서 바뀔 것입니다.
>
> 본 장의 모든 "알려진 문제"는 로컬 실측 + 공식 저장소 deepseek-ai/deepseek-harness 디스커션(2026-08-14 기준)의 공개 피드백에서 가져온 것입니다.

## TL;DR(본 장 핵심, 30초 버전)

1. **rc 단계가 가장 큰 불확실성입니다**: API/설정이 언제든 파괴적으로 변경될 수 있으니, 투자하기 전에 버전 라인을 먼저 고정하세요
2. **플러그인 생태계는 초기 단계입니다**: 공식 패키지는 60+개지만 커버리지가 제한적이고, 서드파티 플러그인이 적으며, 상호작용 형태(TUI)가 빠져 있습니다
3. **크로스플랫폼 약점**: Windows에서는 경로/인코딩 버그(UTF-16, 0x00) 외에도, 포트 예약, LAN 접속, 샌드박스 안정성, WSL 워크스페이스, 자식 프로세스 종료 등 여러 계열의 문제가 있습니다(빠른 참조표는 [12.4](#124-크로스플랫폼-알려진-문제-빠른-참조표) 참고)
4. **성능 경계가 충분히 검증되지 않았습니다**: 고동시성, 대형 코드베이스 시나리오의 공개된 부하 테스트 데이터가 부족합니다
5. **공식 전략 리스크**: 오픈소스 약속 vs 상업화 전환은 도구 선택 시 반드시 고려해야 할 블랙스완입니다

## 12.1 rc 단계의 불안정성

### 파괴적 변경이 언제든 발생

dsh는 rc.1부터 rc.6까지 최소 한 번의 **의존성 단절**을 겪었습니다: 초기 버전의 `@deepseek-ai/*` 패키지 버전 라인 불일치로 플러그인이 설치되지 않는 문제(404/ERR_MODULE_NOT_FOUND)가 있었습니다. rc.6에서 많이 수렴되었지만, rc.7/정식 버전에서 다시 그런 일이 없을 것이라는 **어떤 약속도 없습니다**.

**여러분에게 미치는 실질적 영향**:
- 튜토리얼/플러그인을 작성하면, 2주마다 따라서 수정해야 할 수 있습니다
- 버전 라인을 고정하는 것(`^0.1.0-rc.6`)은 기본 조치이지만, rc 라인 업그레이드가 "상위 호환"인지 "완전히 갈아엎는" 것인지는 공식의 그때그때 판단에 달려 있습니다

> [!WARNING]
> 프로덕션 환경 도입은 신중히 평가하세요. 본 백서 집필 시점에도 공식은 여전히 빠르게 반복하고 있으며, **오늘의 작성법이 내일 폐기될 수 있습니다**.

### 알려진 rc 트러블(로컬/커뮤니티 재현)

| 트러블 | 증상 | 상태 |
|---|---|---|
| link 개발 의존성 단절 | `@deepseek-ai/*`를 로컬 link할 때 ERR_MODULE_NOT_FOUND, npm 설치는 정상 | 원인 파악됨(플랫 폴백 디렉터리 메커니즘), 의존성 라인 고정으로 회피 필요 |
| Windows 경로 0x00 | 중국어/특수문자 경로가 포함된 workspace 생성 실패(ENOENT) | 커뮤니티 피드백 진행 중(#151/#396) |
| fs-sandbox 경쟁 상태 | post-check 경로 검사와 workspace-write 존재 여부 사이에 타이밍 경쟁 존재 | 커뮤니티 피드백 진행 중(#159) |
| TUI 부재 | 공식 examples에 상호작용형 터미널 UI가 없음(커뮤니티 자체 구축은 있으나 공식에 미포함) | 제안 중(#392) |

## 12.2 초기 단계의 플러그인 생태계

**현황**: 공식 패키지는 60+개지만, 생태계 전체는 "초일" 상태입니다.

- **서드파티 플러그인이 적음**: 디스커션의 플러그인 게시물이 폭발적으로 늘고 있지만, 품질이 들쭉날쭉하고 대부분 "첫 플러그인" 연습작입니다
- **상호작용 형태 부재**: headless/JSON-RPC/Web 형태는 갖춰져 있지만, **TUI 등 터미널 상호작용 형태는 공식 예시가 없습니다**(커뮤니티의 deepseek-harness-tui가 실현 가능함을 입증했지만 공식에 포함되지 않음)
- **문서가 코드보다 뒤처짐**: 공식 문서는 아키텍처 위주이고, 시작 경로/트러블슈팅 기록은 커뮤니티 생산에 의존합니다(이것이 바로 본 백서가 존재하는 이유입니다)
- **버전 라인 혼란**: npm에 같은 패키지의 여러 버전 라인이 공존하며, 잘못된 라인을 설치하면 404가 발생합니다

**판단**: 생태계 탐색은 지금 진입하는 것이 초기 보너스입니다(경쟁이 적고 공식의 지원 의지가 강함), 하지만 **"공식 문서대로만 하면 돌아간다"고 기대하지 마세요** —— 트러블슈팅이 일상입니다.

## 12.3 크로스플랫폼 약점

dsh는 macOS/Linux에서는 성숙하게 동작하지만, Windows 지원에는 뚜렷한 **2등 시민 느낌**이 있습니다:

- **경로 처리**: 중국어 경로, 특수문자 경로에 실제 버그가 있음(0x00 절단, ENOENT), 커뮤니티에서 다수 보고(근본 원인 #107, 계열 17+개 게시물)
- **인코딩 문제**: UTF-16 관련 처리에 결함이 있어 터미널 출력이 가끔 깨짐
- **CLI/TUI 논쟁 미결**: 공식 디스커션에 "CLI가 정도다 vs TUI가 상호작용의 미래다"라는 노선 논쟁이 있음(#386), 방향이 명확해지기 전에 터미널 UI 형태에 투자하는 것은 리스크가 있습니다

> 아래의 Windows 계열 문제는 공식 디스커션 발굴 리포트([docs/research/discussion-mining.md](./research/discussion-mining.md), 2026-08-14 수집, rc.6 시대)에서 가져온 것으로, 모두 커뮤니티가 실제로 재현했으며 대부분 아직 수정되지 않았습니다.

### 포트: 기본 3080이 Hyper-V 예약 구간과 충돌(#589)

**증상**: Windows에서 기본 포트 3080으로 시작하면 EACCES 오류가 발생하고, 서비스가 시작되지 않아 web 화면이 열리지 않습니다.
**근본 원인**: Hyper-V/WSL2를 활성화하면, Windows가 동적 포트 구간(3070-3169)을 예약하는데, 3080이 정확히 그 안에 들어갑니다.
**임시 해결법**: 예약 구간 밖의 포트로 바꿉니다(커뮤니티 실측으로 13080 사용 가능).

### LAN을 통한 HTTP 접속 시 RPC 전부 실패(#755)

**증상**: LAN 내에서 HTTP(localhost도 아니고 HTTPS도 아님)로 접속하면 모든 RPC 호출이 실패합니다.
**근본 원인**: `crypto.randomUUID`는 보안 컨텍스트(HTTPS 또는 localhost)에서만 사용 가능한데, LAN의 순수 HTTP는 비보안 컨텍스트에 속합니다.
**임시 해결법**: 공식 수정 없음; HTTPS나 터널(예: Tailscale)로 접속하면 비보안 컨텍스트 제약을 회피할 수 있습니다(원인에 근거한 추론이며, 커뮤니티 게시물 안에서 검증되지는 않음).

### 샌드박스: 임시 디렉터리 정리 후 영구적으로 크래시(#758)

**증상**: Windows에서 샌드박스 임시 디렉터리를 정리한 후 dsh가 영구적으로 크래시되며 자체 복구되지 않습니다(커뮤니티가 P0로 표시), 관련된 안정성 문제 4개가 동반됩니다.
**영향**: 임시 디렉터리를 한 번 정리하면 = 서비스 완전 사용 불가, 자동 복구 경로 없음.
**임시 해결법**: dsh 샌드박스 임시 디렉터리를 정리하지 마세요; 이미 발생했다면 프로세스를 재시작해 복구하세요.

### WSL: 워크스페이스가 /root만 선택 가능(#160)

**증상**: WSL/Ubuntu 환경에서 워크스페이스 선택기가 /root 안의 디렉터리만 선택할 수 있고, 나머지 경로는 선택할 수 없습니다.
**임시 해결법**: 프로젝트를 /root 아래에 두고 사용하세요(제약 안에서는 사용 가능, 제약을 벗어나는 우회 방법은 아직 없음).

### 자식 프로세스: Windows에서 우아한 종료 부재(#717)

**증상**: Windows에서 자식 프로세스 관리 체계가 구조적으로 결여되어 있습니다 —— 우아한 종료 단계가 없고, 손자 프로세스 출력이 잘리며, spill 권한이 적용되지 않고, shellPath가 기본으로 /bin/bash를 가리킵니다(Windows에는 이 경로가 존재하지 않음).
**영향**: 긴 작업 종료가 깔끔하지 않고, 출력이 유실되며, 권한 기대가 실패합니다 —— 이것은 단일 버그가 아니라 플랫폼 어댑팅의 공백입니다.
**임시 해결법**: `taskkill /T`로 프로세스 트리를 수동 정리; shellPath를 Windows의 실제 경로로 명시적으로 설정하세요.

---

> **샌드박스 MSYS 충돌(#1889 실측 시그니처)**: `workspace-write`가 제한된 토큰을 사용할 때, MSYS 계열 shell은 cygheap 초기화 단계에서 바로 죽습니다(`cygheap_user::init: NtSetInformationToken (TokenDefaultDacl), 0xC0000022` / `CreateFileMapping ... Win32 error 5`) —— MSYS 런타임 모델이 제한된 토큰과 직접 충돌하며, 플러그인 레이어에서는 해결책이 없습니다. 이것이 왜 Windows 방안들이 하나같이 `danger-full-access`를 요구하는지를 설명해줍니다(작성자가 게을러서가 아닙니다).

## 12.4 크로스플랫폼 알려진 문제 빠른 참조표

> 본 장의 크로스플랫폼 알려진 문제를 한 표로 정리합니다. 스레드 번호는 모두 공식 디스커션(deepseek-ai/deepseek-harness)의 실제 게시물이며, 2026-08-14 기준입니다.

| 문제 | 환경 | 스레드 | 임시 workaround |
|---|---|---|---|
| 중국어 경로 절단(readUtf16이 단일 바이트로 0을 판단, `开`=U+5F00이 잘림) | Windows | [#107](https://github.com/deepseek-ai/deepseek-harness/discussions/107)(근본 원인; 계열 #151/#396/#563 등 17+ 게시물) | 워크스페이스 경로에 중국어/특수문자 피하기; 커뮤니티가 첨부한 수정 패치로 cherry-pick 가능(#244/#580) |
| 디렉터리 선택기 worker 크래시(koffi 관련) | Windows | [#30](https://github.com/deepseek-ai/deepseek-harness/discussions/30)(계열 #154/#236/#449/#768) | 설치 레이어에서 koffi@3.1.2로 고정(#293); 선택기 크래시는 아직 우회법 없음 |
| 기본 포트 3080이 Hyper-V 예약 구간과 충돌(EACCES) | Windows(Hyper-V/WSL2 활성화) | [#589](https://github.com/deepseek-ai/deepseek-harness/discussions/589) | 예약 구간 밖 포트로 변경(예: 13080) |
| LAN HTTP 접속 시 RPC 전부 실패(crypto.randomUUID가 비보안 컨텍스트) | LAN HTTP(localhost 아님) | [#755](https://github.com/deepseek-ai/deepseek-harness/discussions/755) | HTTPS/터널 접속으로 회피 가능(추론); 공식 수정 없음 |
| 샌드박스 임시 디렉터리 정리 후 영구 크래시(자체 복구 안 됨, P0) | Windows | [#758](https://github.com/deepseek-ai/deepseek-harness/discussions/758) | 샌드박스 임시 디렉터리 정리 금지; 발생 시 프로세스 재시작 필요 |
| WSL 워크스페이스가 /root 안 디렉터리만 선택 가능 | WSL/Ubuntu | [#160](https://github.com/deepseek-ai/deepseek-harness/discussions/160) | 프로젝트를 /root 아래에 두고 사용 |
| Windows 자식 프로세스 우아한 종료 부재(손자 프로세스 출력 절단/spill 실패/shellPath 오류) | Windows | [#717](https://github.com/deepseek-ai/deepseek-harness/discussions/717) | 수동 `taskkill /T`로 정리; shellPath 명시적 설정 |

## 12.5 충분히 검증되지 않은 성능 경계

백서의 benchmark는 **단일 agent, 일반적인 작업 규모**를 커버했으며, 아래 시나리오는 공개된 데이터가 부족합니다:

- **고동시성**: 여러 agent 병렬 실행, 대규모 작업 분배
- **대형 코드베이스**: 수백만 줄 규모 저장소의 컨텍스트 관리, 도구 호출 지연
- **장시간 실행**: 수 시간 연속 실행의 안정성, 메모리 누수 리스크
- **캐시 적중률의 경계**: 97% 실측 적중률은 "대화 패턴 반복"에 의존합니다 —— 완전히 새로운 작업/콜드 스타트 시나리오에서는 눈에 띄게 낮아질 것입니다

## 12.6 성숙한 Agent와의 격차

Claude Code, Codex 등 성숙한 제품과 대조하면, dsh의 격차는 **구조적**입니다(기능 몇 개 보충한다고 따라잡을 수 있는 것이 아닙니다):

| 항목 | dsh(rc.6) | 성숙한 Agent |
|---|---|---|
| 생태계 단계 | 초일, 서드파티 자산이 희소함 | 성숙, 완전한 생태계 |
| 바로 사용 가능성 | profile/플러그인 체계 이해 필요 | 설치하면 바로 사용 |
| 안정성 | rc 시기, 파괴적 변경 리스크 | 안정 버전, 장기 호환 약속 |
| 문서 | 공식은 아키텍처 위주, 시작은 커뮤니티에 의존 | 공식 문서 완비 + 풍부한 튜토리얼 |
| IDE/도구 체인 통합 | 시작 단계 | 깊은 통합 |

**dsh의 포지셔닝**: "바로 사용 가능한 완성차"가 아니라 "프로그래머블 레고 베이스플레이트"입니다. dsh를 선택하는 것 = **자유도**를 선택하는 것이며, 그 대가는 **직접 조립해야 한다**는 것입니다.

## 12.7 공식 전략 리스크

도구를 선택하는 입장에서 반드시 고려해야 할 블랙스완:

- **오픈소스 약속**: MIT 오픈소스에 현재 잡음은 없지만, "공식 레벨 플러그인 체계"는 생태계가 공식의 페이스에 깊이 종속됨을 의미합니다
- **모델 종속 경향**: 공식 기본 경험은 DeepSeek 모델에 편향되어 있습니다(llm 플러그인으로 임의 모델 연결 가능하지만, "공식 최적화"는 자사 모델 위주입니다)
- **상업화 전환**: dsh 사용자 수가 늘어나면, 공식이 관리형 서비스/유료 레이어를 출시할 수 있습니다 —— 오픈소스 버전이 동등한 능력을 유지할 수 있을지는 미지수입니다
- **방향 표류**: rc 시기에는 기능 추가/삭제가 잦습니다(TUI/CLI 노선 논쟁이 바로 그 신호), 잘못된 방향에 베팅하면 = 매몰 비용

## 12.8 백서 자체의 한계

마지막으로, 이 백서 자체에 대해서도 솔직히 말씀드립니다:

- **rc.6 기준으로 작성됨**: 모든 명령어, 설정, 데이터는 rc.6에서 검증되었으며, **새 버전에서는 전부 무효화될 수 있습니다**
- **benchmark 샘플이 제한적**: 단일 머신, 단일 모델, 제한된 작업 집합이며, 권위 있는 평가가 아닙니다
- **중국어 우선**: 영어판은 번역/축약본이라 중국어판 내용보다 뒤처질 수 있습니다
- **커버리지가 완전하지 않음**: dsh 공식 패키지는 60+개지만, 본 핸드북이 깊이 다룬 것은 핵심 경로이며, 롱테일 플러그인은 하나하나 다루지 못했습니다

> **사용 권장사항**: 본 백서를 "rc.6 스냅샷 + 방법론"으로 취급하고, "영원한 경전"으로 여기지 마세요. 버전이 업데이트되면, 먼저 [roadmap 학습 경로](./roadmap.md)와 [치트시트](./cheatsheet.md)의 검수 기준을 한 번 실행해보고, 여러분의 의존성 라인을 업데이트할지 결정하세요.
